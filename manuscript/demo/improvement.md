# 관찰을 개선으로 연결하기

규칙을 추가했다는 사실과 이전에 놓친 실패를 발견하게 됐다는 사실은 다르다. 데모는 반복 실패 후보, 개선할 파일의 범위, 새 평가 사례와 이전 규칙의 비교를 연결한다.[S106]

## 후보에서 평가까지

수집 단계는 실패 범주를 묶어 개선 후보를 만든다. 중복을 구분하는 기준은 유형에 따라 요청·날짜·커밋으로 다르므로 모든 후보가 서로 다른 요청 세 건을 뜻하지는 않는다. 개선 역할은 허용된 지침·검사·평가 파일을 바꾸고 변경 제안을 만든다.[S106]

평가 코드는 봇의 개선 제안에 새 실패 사례를 요구한다. 이전 규칙은 그 실패를 놓치고 새 규칙은 발견하는지 비교하고 기존 평가 사례의 회귀와 임의 변경도 검사한다. 개선 변경은 자동 병합 대상에서 제외된다. 이 연결은 정한 사례의 검출 변화이지 모든 실패 유형의 해결 능력이나 정책 계층 전체의 보존을 입증하지 않는다.[S106]

| 평가에서 비교할 것 | 확인하려는 변화 |
|---|---|
| 새 실패 사례를 이전 규칙에 적용 | 이전 규칙이 그 실패를 놓치는지 |
| 같은 사례를 변경 규칙에 적용 | 변경 규칙이 해당 실패를 발견하는지 |
| 기존 평가 사례를 다시 적용 | 정한 기존 사례에서 회귀나 허용되지 않은 변경이 없는지 |

평가 사례 밖의 실패까지 해결했다는 뜻은 아니다. [4장의 두 개선 루프](../chapters/ch04.md#fig-4-1)에서 이 사례는 하네스 개선 경로에 해당한다.

## 과거 실행 기록은 별도로 읽는다

2026년 10월 12일 리허설은 잘못된 지시를 의도적으로 넣어 같은 오류 유형을 만들었다. [개선 PR #47의 평가 기록](https://github.com/roboco-io/the-software-factory-demo/actions/runs/38223377457/job/114724977130)에서는 새 사례에 대한 이전·변경 규칙의 검출 차이를 볼 수 있다. [검증 PR #48의 검사 기록](https://github.com/roboco-io/the-software-factory-demo/actions/runs/38223958193/job/114726765443)은 같은 오류 형식을 검사가 거부한 결과다. #47은 병합됐고 #48은 병합 없이 닫혔다.[S68]

이 기록은 이번 확인 버전에서 새로 실행한 결과가 아니다. 자연 발생 실패 감소나 장기 효과로 일반화하지 않는다. 운영 안내는 평가 자체의 조작 가능성과 평가 사례가 없는 규칙 삭제를 놓칠 수 있음을 밝힌다.[S106]

이 데모가 개선 변경을 사람에게 넘기는 사실은 보존한다. 책은 허용된 하위 지침·계획의 개선을 별도 평가와 권한 경계 아래 자동으로 적용하는 범위도 인정한다. 확인한 데모가 그러한 무승인 개선 전체를 구현했다는 뜻은 아니다.

## 리더의 판단과 한계

책이 제안하는 최상위 원칙은 자동 개선이 완화할 대상이 아니다. 데모의 수정 가능 파일에는 작업 지침도 들어 있으므로, 허용 파일 목록만으로 원칙이 기술적으로 보호된다고 읽지 않는다. 지침의 모호성을 고칠지, 명확한 지침의 집행을 고칠지 구분하고 결과를 업무에서 다시 관찰한다.

2026년 10월 15일 확인한 고정 버전의 문서와 코드 구조를 설명한다. 데모를 직접 실행하거나 실제 조직의 효과를 검증한 결과는 아니다. 정확한 판본과 확인 범위는 출처에서 추적할 수 있다.
