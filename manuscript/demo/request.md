# 요청에서 실행 가능한 작업까지

요청을 접수하는 일과 실행 권한을 주는 일은 다르다. 리뉴얼 플랫폼은 등록된 저장소의 이슈에 운영자가 실행 라벨을 붙인 요청을 선별한다. 이전 예제의 AI 트리아지·댓글 정리 흐름을 그대로 사용하는 구조는 아니다.[S158]

## 요청과 승인을 잇는 흐름

웹훅 처리기는 서명과 이벤트 종류, 실행 라벨, 운영자의 숫자 ID, 허용된 저장소와 열린 이슈인지 확인한다. 이슈의 요구사항은 수행할 입력이며 제어 평면의 권한이나 지침을 바꿀 허가가 아니다. 모델에 전달하는 프롬프트도 이슈 내용을 외부 입력으로 구분한다.[S158]

이슈별 상태 기계는 중복 전달과 이미 끝난 실행을 구분하고, 예산·동시 실행 조건을 확인해 작업을 시작한다. 입력을 받았다는 사실과 실제 실행을 시작했다는 상태를 분리해 읽어야 한다.

이 흐름에는 저장소·이슈·기준 코드와 공통 실행 절차가 연결된다. 책의 실행계획은 그 안에서 이번 작업에 선택할 순서·의존성·확인 방법이다. 요청 데이터나 상태 기계를 그 계획 자체와 동일시하지 않는다. 복잡한 요구의 계획 품질과 사업적 적절성은 별도로 확인할 과제다.

## 리더의 판단과 한계

운영자가 시작을 허용하는 것은 현재 데모의 선택이다. 책의 일반 원칙은 필요한 정책·증거·권한 조건을 갖춘 범위의 시작 판단도 자동화할 수 있다는 것이다. 운영자 허용만으로 요청의 완전성이나 목표 달성을 보장하지 않는다.

2026년 11월 9일 확인한 리뉴얼 플랫폼의 고정 판본을 기준으로 썼다. 문서·코드의 정적 구조를 확인했으며, 에이전트 실행·로그인·병합을 직접 시험하거나 운영 효과를 검증한 결과는 아니다.
