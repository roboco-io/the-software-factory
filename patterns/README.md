# 패턴 언어

15개 패턴 후보다. 공개 사례와 반례를 축적하여 검증한다. 현재 어떤 패턴도 효과 검증 완료로 표시하지 않는다.

각 카드의 해결 구조와 기대 효과는 적용 조건 아래 평가할 저자 제안이다. 초고의 내용 검토와 실제 업무의 효과 평가, 저자의 편집 확정은 별도 상태로 관리한다. 카드의 비용 절에서는 그 패턴이 특히 늘리는 부담과 감수할 조건을, 검증 절에서는 다음 판단에 쓸 관찰을 읽는다. 적용 조건이 바뀌면 기존 기준으로 비교할 수 있는지 먼저 확인한다.

|---|---|---|---|
| [P01](../manuscript/patterns/p01.md) | 의도의 명시화 | 모호한 요구가 실행자마다 다른 결과를 만든다. | P02, P03, P15 |
| [P02](../manuscript/patterns/p02.md) | 정책과 계획의 분리 | 수행 방법을 고치면서 지켜야 할 경계까지 함께 바뀐다. | P01, P03, P10 |
| [P03](../manuscript/patterns/p03.md) | 실행 가능한 계약 | 말로 합의한 내용을 실행 단계에서 검증할 수 없다. | P02, P04, P06 |
| [P04](../manuscript/patterns/p04.md) | 검증 가능한 작업 단위 | 큰 작업은 실패 원인과 완료 여부를 판단하기 어렵다. | P03, P05, P09 |
| [P05](../manuscript/patterns/p05.md) | 필요한 맥락의 공급 | 에이전트가 오래되거나 관련 없는 정보를 근거로 판단한다. | P01, P04, P13 |
| [P06](../manuscript/patterns/p06.md) | 증거 기반 완료 | 완료 보고와 실제 요구 충족 사이에 차이가 생긴다. | P03, P07, P13 |
| [P07](../manuscript/patterns/p07.md) | 독립된 검증 | 실행자가 만든 검증이 실행자의 오해를 반복한다. | P06, P10, P11 |
| [P08](../manuscript/patterns/p08.md) | 조합 단위의 선별 | 모델 순위가 실제 프로젝트 성능을 예측하지 못한다. | P03, P07, P09 |
| [P09](../manuscript/patterns/p09.md) | 실행 주체의 교체 | 도구 변경이 업무의 기준과 작업 기록을 깨뜨린다. | P03, P08, P13 |
| [P10](../manuscript/patterns/p10.md) | 범위가 정해진 자율성 | 작업 권한이 커지면서 실패의 영향 범위가 불명확해진다. | P02, P07, P11 |
| [P11](../manuscript/patterns/p11.md) | 예외를 통한 개입 | 모든 실행을 사람이 검토해 생산 흐름이 정체된다. | P06, P10, P12 |
| [P12](../manuscript/patterns/p12.md) | 결정에 필요한 보고 | 로그는 많지만 사람이 무엇을 결정해야 하는지 알 수 없다. | P11, P13, P14 |
| [P13](../manuscript/patterns/p13.md) | 의도부터 결과까지 추적 | 결과의 원인이 된 정책과 계획 버전을 확인할 수 없다. | P01, P06, P12, P15 |
| [P14](../manuscript/patterns/p14.md) | 흐름에 맞춘 권한과 팀 경계 | 빠른 구현 후에도 부서 간 인계와 승인 대기가 남는다. | P04, P11, P12 |
| [P15](../manuscript/patterns/p15.md) | 검증을 거치는 개선 | 자동화가 평가 기준을 바꿔 성과가 좋아 보이게 만든다. | P02, P07, P13 |
