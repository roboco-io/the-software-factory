# 기획안: 비즈니스 목표 중심 자동화로의 단계적 확장

- 작성일: 2026-10-21
- 대상: `roboco-io/the-software-factory-demo`
- 상태: 기획·외부 실행자 검토용. 구현·운영 실험에 착수한 상태가 아니다.
- 현재 코드 확인 기준: `a5bba6b7075222e7c0204f6822fba74977d313f4`

## 권고 실행 방식

**초기 기반은 저장소 소유자가 지정한 외부의 신뢰할 수 있는 실행자가 구축할 것을 권고한다.** 외부 실행자는 현재 팩토리의 `implement`·`improve` 자동 역할 밖에서 작업하며, 저장소의 규칙과 검토·병합 절차를 따르는 사람 또는 그 사람이 관리하는 개발 에이전트다.

이 이슈는 여러 단계의 기획·조정용 상위 이슈로 관리한다. 현재 자동 구현 요청 한 건으로 배정하지 않는다. 신뢰된 실행자가 작은 구현 계획과 하위 이슈·PR로 나누고, 각 단계의 증거를 확인한 뒤 다음 단계로 진행한다. 기존 금지 경로를 풀거나 에이전트가 자기 승인·보안·평가 기준을 바꾸게 하는 방식으로 시작하지 않는다. 실행 승인 명령은 이 기획 전달에 포함하지 않는다.

초기 구축이 검증된 뒤에는 명시적으로 위임한 제품 개선·관측·후속 선택을 자동화한다. 외부 실행자의 초기 참여가 모든 목표와 모든 변경에 영구적인 사람 승인을 요구하는 원칙을 뜻하지는 않는다.

## 목적과 기대 결과

현재 데모의 요청→구현→검토→배포 흐름에 **사업·고객 목표→가설→실행→운영 관측→다음 선택**의 연결을 추가한다. 다음 세 결과를 별도로 기록한다.

1. 목표 중심으로 반복 실행할 능력을 구현했는가.
2. 그 제어 흐름이 제한된 조건에서 실제로 동작했는가.
3. 실제 사용자·사업 결과가 목표를 충족했는가.

초기 구축의 완료는 1과 제한된 2에 관한 증거다. 사업 성과의 달성은 운영 관측 후 별도로 판정한다. 측정되지 않은 기준선·개선율을 만들어 넣지 않는다.

## 현재 구조에서 출발할 지점

확인한 주 실행 경로에는 구현 역할의 팩토리 핵심 수정 금지, 제한된 자가 개선 경로, 권한자의 실행 시작, 배포 성공 시 기능 이슈 종료가 있다. 주요 집계는 실행·실패·비용이다. 이번 확인은 선택 경로의 정적 조사이며 저장소 전체의 기능 부재를 입증한 것은 아니다.

## 대표 시나리오

첫 시나리오는 **사용자가 발견한 문제를 운영자가 처리할 수 있는 피드백으로 전달하도록 돕는 것**으로 제안한다. 기존 피드백 기능을 활용하되 이 시나리오와 계측의 타당성은 0단계에서 확인한다.

제품 지표 후보는 ‘관측 가능한 피드백 입력 시작 중 서버에 정상 수락된 제출의 비율’이다. 목표는 버튼 문구를 바꾸는 일 같은 구현 수단과 분리한다. 실제 문제와 기준선을 확인한 뒤 문구·오류 안내·제출 흐름 등 개선 가설을 선택한다.

이 비율은 고객 문제 전달을 나타내는 제품 지표다. 매출·고객 만족이나 문제 해결 자체를 입증하는 수치로 확대하지 않는다. 후속 운영에서 처리 가능한 피드백이 늘었는지와 운영 부담도 함께 확인한다.

## 최소 구성과 데이터 흐름

목표 정의, 관측, 의사결정, 실행 연결, 이력의 다섯 책임을 구분한다. 기존 상태 저장·phased stage·권한 검사·실행 기록을 재사용할 수 있는지 먼저 확인한다.

- **목표 계약**: 고객 문제·사업 가설·성공/보호 지표·기준선·관찰 기간·예산·허용 행동·미확인/중단/완료 조건·책임자·판본을 보존한다.
- **관측 경로**: 수집 기간과 데이터 품질·누락·중복을 표시하고 목표/배포 판본과 연결한다. 관측 실패를 ‘변화 없음’으로 쓰지 않는다.
- **목표 판정**: 관측과 정책을 대조해 대기·가설 선택·재계획·달성·중단·사람 판단을 구분한다. 통계적 불확실성과 외부 변화도 남긴다.
- **실행 연결**: 선택한 가설을 작은 작업으로 만들고 기존 구현·검토·배포에 연결한다. 같은 목표·판본·가설의 중복 착수를 막는다.
- **추적과 보고**: 목표 ID/판본→가설→하위 이슈/PR→배포 커밋→관측 기간→판정→다음 행동을 따라갈 수 있게 한다.

기능 이슈는 현재처럼 배포 후 닫을 수 있다. 상위 목표는 그때 ‘관찰 대기’로 이동하며 사업 목표 달성과 구분한다. 목표의 제어 상태는 최소한 기획·기준선 수집·준비·실행·관찰·판정·달성/중단/일시정지를 구분한다. 데이터 부족이나 권한·정책 충돌은 성공으로 처리하지 않는다.

## 단계별 여정과 수용 기준

### 0단계 — 신뢰된 실행자의 설계·범위 고정

- 최신 main과 기존 접수·권한·예산·관측·작업 상태를 조사한다.
- 목표와 구현/배포 완료를 구분하는 설계, 영향 파일과 의존 순서, 외부 자격 증명·권한 변경, 단계별 검증 계획을 문서화한다.
- 실제 목표 책임자와 정책·운영 책임자를 지정한다. 담당자는 제어 루프를 운영하기 전에 목표/표본 기준·관찰 기간·목표/기간별 지출·동시 실행·최대 반복·중단 임계값을 수치로 확정한다. 이 문서는 자료 없는 임계값을 대신 지정하지 않는다.
- 작은 하위 이슈와 PR로 나눈다. 팩토리 코어·워크플로 변경은 외부 실행자가 별도 브랜치에서 수행하고 기존 검토·CODEOWNERS 절차로 통합한다.

**수용 기준:** 실행 대상·책임·허용 범위·필수 파라미터·단계별 검증이 명확하며, 현재 자동 역할에 이 상위 이슈를 그대로 맡기지 않는 실행 계획이 있다.

### 1단계 — 목표 계약과 독립된 상태

- 목표와 기능 작업의 상태를 분리하고 목표 판본·가설·책임·예산·보호 조건을 저장한다.
- 필수 조건이 빠진 목표는 실행 준비 상태가 될 수 없게 한다.
- 모델이 목표값·보호 조건·평가 기준을 임의로 바꾸지 못하게 한다.

**수용 기준:** 기능 배포 후 상위 목표는 관찰 대기로 남는다. 목표 변경에는 판본과 권한 근거가 남으며 이전 관측을 새 기준의 성공 증거로 재사용하지 않는다.

### 2단계 — 기준선과 관측 신뢰성

- 대표 시나리오의 지표 정의·분모·관찰 기간·계측 범위를 정하고 실제 기준선을 얻는다.
- 데이터의 미수집·지연·동의/접근 제한·낮은 표본을 구분한다. 계측 범위 밖의 활동을 0이나 성공으로 채우지 않는다.
- 초기 시험 데이터와 실제 사용자 관측을 표시한다. 테스트 데이터로 루프가 동작했다는 결과를 실제 사업 개선으로 쓰지 않는다.

**수용 기준:** 지표가 정한 자료에서 재계산 가능하고, 부족/중복/지연된 관측을 성공 판정에서 구분한다. 개인정보나 피드백 본문을 성과 계측에 불필요하게 수집·공개하지 않는다.

### 3단계 — 목표에서 작은 작업으로

- 에이전트가 목표·맥락·관측을 근거로 개선 가설과 작은 작업을 제안한다.
- 초기에는 제안 모드로 경계 준수를 검증한다. 정책으로 위임한 범위와 필수 증거를 갖춘 뒤에 자동 실행을 허용한다.
- 기존 작업 큐·구현/검토/배포 경로를 재사용한다. 중복 제안과 동시 작업 충돌을 제어한다.

**수용 기준:** 하위 작업에 목표·가설·수용 기준·예산이 연결되며, 재시도나 중복 이벤트가 같은 작업을 두 번 만들거나 예산을 초과하게 하지 않는다.

### 4단계 — 관측에서 다음 선택으로

- 사전에 정한 기간/표본 조건을 충족하면 관측하고 유지·다음 가설·재계획·달성·중단을 판단한다.
- 목표별·일별/기간별 지출과 반복 횟수를 집행하고 예약·재개·중단 상태를 보존한다.
- 개선 근거가 부족하면 관찰을 보강하거나 멈춘다. 목표 달성을 위해 평가 지표나 보호 조건을 바꾸지 않는다.

**수용 기준:** ‘개선 관측’, ‘개선 없음’, ‘관측 부족’, ‘보호 조건 위반’, ‘예산/기간 종료’가 서로 다른 다음 행동으로 이어진다. 실제 개선을 목표에 귀속할 근거가 부족하면 그 한계를 보고한다.

### 5단계 — 제한된 운영 실험과 확대 판단

- 신뢰된 실행자는 종료·보류·이관·복구·중복 방지의 검증 결과를 확인하고 제한된 범위에서 관측 가능한 운영 실험을 진행한다.
- 도입한 제어 능력, 실제 동작한 반복, 제품/사업 결과를 별도로 보고한다.
- 결과에 따라 다음 자동화 범위와 투자, 추가 계측을 정한다.

**수용 기준:** 한 목표의 전체 경로와 비용·개입·남은 불확실성을 재검토할 수 있다. 기능 이슈를 닫거나 테스트를 통과한 사실만으로 이 상위 목표를 완료하지 않는다.

## 운영·권한 원칙

- 자동화는 명시된 대상·행동·기간·예산과 증거 안에서 수행한다. 단방향 결정도 사안에 따라 위임할 수 있지만 정보 보호와 최소 권한 경계를 완화하지 않는다.
- 권한을 원복할 수 있어도 이미 허용 범위 밖으로 읽히거나 전달된 정보는 회수 보장을 할 수 없다. 필요한 데이터 접근·출력·전송 범위를 실행 전에 제한한다.
- 실행 주체는 자기 권한·성공 조건·안전 기준을 스스로 완화하지 않는다. 위임하지 않은 사업적 선택은 해당 책임자에게 넘긴다.
- 읽지 못한 관측·판단 불능·정책 충돌은 보류한다. 사람에게 넘긴 상태도 목표 추적에서 유실시키지 않는다.
- 프로덕션 사고 대응은 성과 실험보다 우선한다. 사고 처리·되돌리기 중 관련 목표의 새 실행을 일시 정지하고 복구 판본과 관측 기간을 재확인한다.
- 비동기 작업·예약 재실행·배포 후 관측에서 목표 판본과 실제 상태를 다시 확인한다. 중복 이벤트에는 동일한 결정을 중복 집행하지 않는다.

## 검증과 완료 보고

구현자는 기존 저장소 지침의 타입·린트·단위·API·웹 E2E 검사와 관련 워크플로 검사를 적용한다. 초기화/업그레이드와 다음 회귀 조건을 반드시 포함한다.

- 정상 관측에 따른 다음 가설 선택과 한 번만 실행되는 후속 작업.
- 데이터/표본 부족과 읽기 실패에서 자동 성공·무한 재시도가 발생하지 않음.
- 보호 조건 위반·예산/시간 종료·실행 권한 부족에서 중단/보류가 집행됨.
- 중복 이벤트·늦은 관측·판본 변경·중간 재시작에서 잘못된 목표에 실행/관측이 붙지 않음.
- 기능 배포 성공과 목표 성과 판정의 분리.
- 목표 지표·보안 조건을 임의로 낮춘 제안의 거부.
- 사고 복구 중 목표 실행의 일시정지와 복구 후 재판정.

최종 보고는 변경 설계, 실행한 검사/리허설, 실제 관측 범위, 비용, 사람이 한 결정, 중단/미해결 조건을 구분한다. 각 단계는 별도 수용하고 이 상위 이슈에서 진행을 추적한다.

## 첫 실행 과제

**외부의 신뢰된 실행자에게 우선 요청할 것은 0단계의 상세 설계와 하위 작업 분해다.** 목표 계약·상태·관측·판정·실행 연결의 책임과 기존 코드와의 통합을 확정하고, 1단계의 작은 구현 PR부터 진행한다. 이 기획 전달 자체로 기존 팩토리의 자동 구현·워크플로를 시작하지 않는다.
