# [기획] Pstack·Tstack 원리를 적용한 검증 자산 수명주기와 증거 기반 반영

## 목적과 범위

관련 상위 기획: [#79 비즈니스 목표 중심 자동화로의 단계적 확장](https://github.com/roboco-io/the-software-factory-demo/issues/79).

검증 방법을 프로젝트 자산으로 유지하고, 현재 변경의 실제 실행 증거를 리뷰·CI·반영 조건에 연결한다. 단순히 스킬을 설치하거나 모델이 합의했다는 표시를 추가하는 것이 목표가 아니다. 사용자 경로가 실제로 동작하는지 확인할 능력, 안전한 자동 반영 경로, 운영 이후 목표 관찰을 구분한다.

이 이슈는 **설계·조정용 적용 계획**이다. 현재 팩토리에 통째로 자동 구현을 맡기는 요청이 아니다. 초기 제어·권한·증거 기반은 저장소 소유자가 지정한 신뢰할 수 있는 외부 실행자(사람 또는 그 사람이 관리하는 개발 에이전트)가 단계별 PR로 구축할 것을 권고한다. 이슈 생성은 실행 승인·운영 변경·보호 규칙 완화의 허가를 포함하지 않는다. 초기 조건이 검증된 뒤 정책으로 위임한 범위는 개별 승인 없이 자동화할 수 있다.

## 현재 구현에서 출발할 곳

조사 기준은 main `b925518f535b49f3383b23db52cc66e8139ce042`다. 아래 문서/코드를 정적으로 읽었으며 실행하지 않았다. 착수 시 최신 main과 진행 PR을 다시 확인하고, 아래 요소가 없는 것으로 가정해 중복 구현하지 않는다.

- [README](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/README.md): 현재 예제 서비스는 책 토론 포럼 conveyor다. 기존 요청·구현·리뷰·병합·배포·개선 흐름에서 출발한다.
- [CI](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/.github/workflows/ci.yml): 타입/린트/단위/API/E2E, 수정 증거·평가와 보안 검사를 재사용한다. 계획과 판정에서 base 코드를 읽는 기존 경계를 보존한다.
- [포럼 사용자 여정 E2E](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/apps/web/e2e/forum-topic.spec.ts): 절에 토론 열기→답글/스레드→다른 사용자의 추천을 다룬다. 고정 책 데이터가 필요한 로컬/CI 전용 경로다. 이를 운영 사용자 계정으로 실행하지 않는다.
- [반영 판단](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/packages/factory/src/stages/gate.ts): 현재 head의 검사·리뷰·위험·프리뷰·사람 조치와 실제 병합을 연결한다. `checkState`는 완료된 skipped/neutral도 pass로 처리하므로 아래 새 증거의 의미와 대조해야 한다. 이를 근거 없이 전부 실패로 바꾸지는 않는다. 기존 정책상 비대상과 미실행/미확인을 구분한다.

선택 파일의 확인은 전체 기능 부재나 현재 설정의 실제 강제성에 대한 감사가 아니다.

## 단계별 적용과 완료 조건

### 0. 실행 계약과 설계 고정

- [ ] 현재 CI·리뷰·실행 기록·권한/정책·검증 자료를 목록화하고 새 기능과 재사용할 요소를 구분한다.
- [ ] 대표 사용자 여정, 목표와 비기능 조건, 허용 환경/데이터/외부 행동, 예산·반복·시간 한도, 소유자와 변경 권한을 문서화한다.
- [ ] 검증 스킬/지도, 실행 증거, 리뷰 지적 장부, 반영 판정 사이의 데이터·상태·신뢰 경계를 설계한다. 작은 하위 이슈/PR과 선행 관계로 나눈다.

**완료 증거:** 승인된 범위와 미확인 조건이 명확하며 현재 product implement/improve 역할에 자기 권한/성공 기준/필수 검사를 완화할 권한을 주지 않는 구현 계획이 있다.

### 1. 프로젝트별 검증 지도와 실행 가능한 검증 스킬

- [ ] 기존 E2E/실행 도구를 우선 재사용해 주요 사용자 여정의 진입점·준비 조건·조작·기대 상태·부수 효과·증거를 연결한다. 초기 범위와 미확인 기능을 표시한다.
- [ ] 빈 시험 데이터에서 사용 가능한 상태까지의 준비, 인스턴스/빌드/권한의 상태 확인, 조작, 증거 수집과 정리 절차를 제공한다.
- [ ] 자신이 시작한 자원만 정리하고 사용자의 공유 세션을 중복 조작하지 않는다. 실행 실패 뒤에도 정리하며 증거는 남긴다.
- [ ] 생성한 절차를 실제 여정에서 한번 실행해 작동을 입증한다. 화면 캡처만으로 결과를 확정하지 않고 행동과 후속 상태를 함께 기록한다.

**완료 증거:** 로컬/CI에서 재현 가능한 절차와 실제 증거가 있고, 계정·고정 데이터·외부 상태 부족 때문에 실행하지 못한 경우는 실패/미확인으로 보고한다. 초기 검증 생성 성공을 제품 전체 통과로 표시하지 않는다.

### 2. 검증 자산 유지관리와 제품 회귀의 분리

- [ ] 기능별 소스 조사와 실제 실행으로 지도/스킬의 드리프트를 확인한다.
- [ ] 낡은 설명, 검증 도구가 구동하지 못하는 경우, 제품이 계약을 어긴 경우를 구분한다.
- [ ] 유지관리 변경은 검증 자산으로 제한한다. 제품 회귀는 별도 수정으로 연결하고, 현재 동작에 맞춰 기대 결과를 낮추지 않는다.
- [ ] 의도·정책이 바뀐 경우에는 권한 근거와 판본을 연결한 뒤 기대 결과를 갱신한다.

**완료 증거:** 설명만 낡은 사례·검증 도구 문제·제품 회귀를 각각 넣은 리허설에서 올바르게 분류한다. 수정된 도구는 재실행하고 정상 여정의 회귀도 확인한다.

### 3. 실행 증거와 정책상 반영 조건의 연결

- [ ] 증거에 변경/base 버전, 적용 의도/정책·검증 자산 판본, 기능/환경/전제, 실제 행동/결과와 수행 상태, 실패/미확인 이유를 연결한다.
- [ ] 보고서 자체를 신뢰하지 않는다. 신뢰할 수 있는 실행 경로의 출처와 현재 변경과의 일치, 유효 범위를 검증한다. 제품 변경이 검증 기준과 판정기를 함께 낮추지 못하게 한다.
- [ ] 통과·정책상 비대상·실패·미실행/미확인을 구분한다. skipped/neutral의 허용은 검사별 정책에 명시하고, 비대상 근거가 없거나 필수 실행 결과가 없으면 자동 통과하지 않는다.
- [ ] 현재 head와 유효한 리뷰/검사·필수 사람 조치·실제 권한을 반영 직전에 다시 대조한다. 보호 브랜치·CODEOWNERS·보안 검사를 우회하지 않는다.

**완료 증거:** 오래된 증거, 다른 환경/변경의 보고서, 보고서 조작, 필수 검사 생략/누락, 검토 뒤 코드 변경, 미완료 사람 조치에서 반영을 막는다. 반대로 허용된 정상 변경은 새 사람 승인을 불필요하게 요구하지 않는다. 기존 비대상 검사의 정상 동작도 보존한다.

### 4. 한도가 있는 리뷰와 비동기 대기의 책임

- [ ] 현재 리뷰 경로를 재사용해 지적 ID·조건·근거·심각도·수용/반박/범위 밖·해결 상태를 유지한다.
- [ ] 반복 횟수·비용·시간 한도, 재검토 범위와 종료/보류 조건을 정한다. 특정 모델이나 스킬 기본값을 조직의 상위 원칙으로 고정하지 않는다.
- [ ] 다중모델 패널은 선택 기능이다. 필요한 모델 부재·오류·무응답·미합의·한도 종료를 승인으로 처리하지 않는다. 제공자 수/점수/합의만으로 독립성·보안을 보장하지 않는다.
- [ ] 한 작업의 조정/대기 책임을 하나로 두고 재시작·중복 이벤트·새 푸시에서 현재 상태를 이어받는다. 모든 봇 지적을 무조건 수정하지 않고 근거로 판단한다.

**완료 증거:** 오탐 반박·미해결 결함·반복 한도·늦은 리뷰·새 head·중복 이벤트를 시험한다. 필요한 사람 판단과 단순 봇의 권고를 구분하며 모델의 확신으로 명시적 확인 의무를 해제하지 않는다.

### 5. 운영 결과와 개선의 연결

- [ ] 기능 수용, 병합, 배포, 배포 후 사용자 결과를 다른 상태로 기록한다. 이 이슈만으로 #79의 사업 목표가 달성됐다고 완료하지 않는다.
- [ ] 반복 실수에는 규칙과 집행 수단을 짝짓고 새 장치가 과거 실패를 거부하는지·정상 작업을 과도하게 막지 않는지 확인한다.
- [ ] 검증 범위·실제 실행률/미확인·오탐/누락·전체 비용/사람 지원·판정 대기를 관측한다. 측정 전 성과 수치나 표본 기준을 만들어 넣지 않는다.

**완료 증거:** 한 변경의 목표→지도/증거→리뷰→CI/판정→반영→운영 관찰을 추적할 수 있고, 미확인과 남은 위험을 찾을 수 있다. 확대·보완·중단의 판단 자료를 #79에 연결한다.

## 구현·검증 원칙

- 검증 생성·운영은 초기에는 격리된 로컬/CI의 합성 데이터로 수행한다. 운영 쓰기·삭제·권한 확대·정책 변경은 해당 위임을 별도로 확인한다.
- 현재 자동화가 허용된 제품 변경은 조건 충족 시 개별 승인 없이 진행할 수 있다. 초기 신뢰 기반 구축에 외부 실행자를 권고하는 것이 영구적인 전수 사람 승인을 요구한다는 뜻은 아니다.
- 코드 검토의 합의, 컴파일 성공, 스크린샷 존재, PR 병합은 각각의 확인 범위만 증명한다. 다른 범위를 임의로 채우지 않는다.
- 기존 테스트를 전부 대체하거나 Pstack/Tstack 전체를 설치하는 방식으로 시작하지 않는다. 현재 하네스와 정책에 맞게 원리를 적용하고 재사용 부분의 출처를 남긴다.
- 이번 이슈 생성은 설계 전달이다. 실행 승인 명령·승인 라벨·직접 코드 변경·워크플로 수동 실행을 포함하지 않는다.
