# 사실·출처 리뷰 정책

- 축 ID: `evidence` / 의견 접두어 `E`
- 공통 규칙: [README](README.md)의 버전 고정·읽기 전용·우선순위·의견 형식·상태를 따른다.

## 이 리뷰가 답하는 질문

이 리뷰는 원고의 각 주장이 인용한 출처가 실제로 말하는 범위 안에 있는지 확인한다. 이 책은 공개 1차 자료를 근거로 삼고, 직접 확인한 관찰·사례 주체의 보고·저자 해석·설계 제안을 구분한다고 독자에게 약속한다([편집 정책](../editorial-policy.md), [근거 규칙](../../research/evidence-policy.md)). 근거가 주장보다 약한데 주장이 강하게 쓰이면, 리더는 검증되지 않은 효과를 믿고 투자나 조직 변경을 결정할 수 있다. 그래서 이 축의 중대한 오류는 P0이 될 수 있다.

이 리뷰는 논증이 설득력 있는지 판정하지 않는다. 그것은 [논증·구조 리뷰](01-argument.md)가 본다. 이 리뷰는 개별 주장과 근거의 대응을 본다.

## 읽어야 할 자료

대상 원고, 해당 장의 주장 메모(`research/claims/chNN.json`의 `claims[].location·type·note`), 출처 대장(`research/sources.json`의 해당 ID 항목)을 읽는다. 출처 항목에서는 `verification_status`, `verification_scope`, `limit`, `published_on`, `checked_on`, `repository_snapshot`, `usage_review`를 확인한다. 공통 구현 예제를 다루는 장은 `research/cases/software-factory-demo.md`의 고정 버전과 장별 범위를 함께 읽는다. 『More Effective Agile』과 대응하는 장은 `research/mcconnell/chapter-map.md`의 확인 범위를 읽는다.

## 원문 대조의 범위

모든 문장을 원문과 대조하지 않는다. 다음 주장은 반드시 원문과 대조한다.

- 리더의 결정을 바꾸는 주장: 효과·인과·위험·비용에 관한 주장.
- 수치·날짜·인물·조직명·제품명·버전.
- 직접 인용.
- 해당 장에서 처음 등장하는 출처의 첫 사용.

원문은 출처 대장의 URL을 직접 열어 확인한다. 검색 결과의 요약은 원문 확인을 대신하지 않는다. 접근하지 못했거나 일부만 읽었다면 그 사실을 보고서의 "확인하지 못한 것"에 적고, 해당 주장은 "원문 미대조"로 남긴다. 접근 실패를 근거 부족으로 판정하지 않는다. 웹 자료 조사는 가능하면 하위 에이전트에 위임하고 요약만 받는다.

## 검토 기준

### 1. 주장의 유형과 출처의 성격이 맞는가

각 주장을 근거 규칙의 여섯 성격으로 분류한다: 직접 확인한 관찰, 사례 주체의 보고, 원문의 설명 예시, 저자 해석, 설계 제안, 검증 결과. 그리고 본문 표현이 그 성격을 넘는지 확인한다. 다음은 P0 또는 P1이다.

| 넘어선 형태 | 등급 |
|---|---|
| 출처에 없는 사례·대화·수치·성과를 본문이 제시함 | P0 |
| 원문의 설명 예시를 실제 사건이나 성과로 서술함 | P0 |
| 사례 주체의 자체 보고를 독립 검증된 효과로 서술함 | P1 (결론을 떠받치면 P0) |
| 문서·코드의 존재를 실제 실행으로, 실행을 운영 성과로 서술함 | P1 |
| 한 사례의 결과를 모든 조직에 적용되는 법칙으로 일반화함 | P1 |
| 저자 해석을 출처의 주장처럼 출처 표식 뒤에 붙임 | P1 |

### 2. 확인 수준이 서로 섞이지 않았는가

근거 규칙은 확인 상태를 미확인, 관련 부분 확인, 코드 구조 확인, 실행 확인, 운영 성과 확인으로 나눈다. 본문과 주장 메모가 실제 확인 수준보다 높은 표현을 쓰면 의견으로 기록한다. 예를 들어 저장소 문서만 읽은 경우 "테스트를 실행해 확인했다"고 쓸 수 없다.

### 3. 표식·주장 메모·출처 대장이 일치하는가

본문의 `[Sxx]` 표식이 가리키는 출처가 그 문장의 내용을 실제로 다루는지 확인한다. 주장 메모의 `location`이 실제 문단을 가리키는지, `type`이 본문 표현과 맞는지, 출처 대장의 `limit`이 본문에서 지켜지는지 확인한다. 자동 검사(`scripts/check_project.py`)는 표식과 대장의 ID 연결만 확인하므로, 의미의 일치는 리뷰어가 직접 본다. 핵심 주장인데 주장 메모가 없으면 P2다.

### 4. 시점이 있는 정보에 시점이 붙어 있는가

모델·도구의 능력, 가격, 벤치마크, 제품 기능처럼 바뀌는 정보에는 자료의 시점이 있어야 한다. 특정 시점의 연구를 현재의 보편 사실로 쓰면 P1이다. 리뷰 시점에 후속 자료나 정정이 있는지 확인하고, 있으면 보고한다. 공통 구현 예제는 고정한 커밋의 내용만 근거로 삼는다.

### 5. 인용과 요약의 양이 한도 안에 있는가

별도 허용이 확인되지 않은 일반 웹 자료는 직접 인용을 출처당 25단어 이하, 요약·의역을 출처당 200단어 이내로 제한한다(`AGENTS.md` "출처 ID와 인용"). 같은 출처를 여러 장과 조사 파일에서 쓴 양은 합산하므로, 대상 출처 ID로 저장소 전체를 검색해 누적 사용량을 확인한다. 한국어 어절 수의 자동 집계만으로 준수를 확정하지 않는다. 따옴표 안에 의역이 들어 있으면 P1이다.

### 6. 이 책에 고유한 제한을 지키는가

IDD의 최초 명명이나 독점 정의를 주장하지 않는가. 『More Effective Agile』의 본문을 읽지 않은 항목을 참고 도서의 주장으로 요약하거나 반박하지 않는가. 참고 도서 대응은 공개 목차와 공개 소개 범위의 "주제에 대한 재고찰"로 표시되어 있는가. 로보코 자료는 로보코의 자체 설명으로 표시되어 있는가. 위반은 P1이고, 참고 도서 본문을 읽은 것처럼 쓴 경우는 P0이다.

## 하지 않는 일

출처 대장과 주장 메모를 직접 수정하지 않는다. 새 자료를 찾았으면 보고서에 제목·작성 주체·URL·발표일·확인일·확인 범위·한계를 적고, 대장 갱신은 수정 단계에서 수행한다. 확인하지 못한 날짜나 정보를 추정해 채우지 않는다. 원문을 대량 번역하거나 보고서에 옮겨 담지 않는다. 근거가 없다는 이유만으로 설계 제안을 탈락시키지 않는다. 제안은 제안으로 표시되고 효과 단정이 없으면 출판할 수 있다.
