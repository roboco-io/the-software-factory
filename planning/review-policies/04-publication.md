# 출판 준비 리뷰 정책

- 축 ID: `publication` / 의견 접두어 `U`
- 공통 규칙: [README](README.md)의 버전 고정·읽기 전용·우선순위·의견 형식·상태를 따른다.
- 상태: README의 정책 상태를 따른다. 2026-10-15 7장 시범 결과로 조정(D28).

## 이 리뷰가 답하는 질문

이 책은 `https://factory.roboco.io`에 공개 초안(`book-publication.json`의 `status: preview`)으로 발행된다. 웹 독서판은 `manuscript/`의 원고에서 생성되고, 읽기 진도와 "읽은 뒤 수정됨" 표시를 제공하며, 독자에게 체인지 로그와 라이선스를 약속한다. 이 리뷰는 독자가 받는 공개본이 원고를 손상 없이 전달하고, 이 약속들이 실제로 지켜지는지 확인한다.

이 리뷰는 원고 내용의 옳고 그름을 판정하지 않는다. 원고가 공개본으로 바뀌는 과정과 공개에 딸린 정보(메타데이터·변경 기록·라이선스·접근성)를 본다.

## 읽어야 할 자료

`website/README.md`, `website/content-manifest.json`, `book-publication.json`, `LICENSE.md`, `CHANGELOG.md`, `skills/book-changelog/references/policy.md`, `book_project.json`, `outline/toc.md`, `README.md`를 읽는다. 변경 범위를 리뷰할 때는 기준 버전과 직전 공개 커밋 사이의 `git diff --stat <직전 공개 커밋>..<기준 커밋>`으로 바뀐 원고 파일을 특정한다.

### 직전 공개 커밋

직전 공개 커밋은 리뷰 시작 시점의 `origin/main`이 가리키는 커밋으로 정한다. 리뷰어는 `git fetch origin` 뒤 `git rev-parse origin/main`으로 이 커밋을 확인해 매니페스트에 적는다. 다만 푸시된 커밋이 배포까지 되었다는 보장은 없다. 그래서 대상 장의 배포 사이트 페이지(`https://factory.roboco.io/book/chNN/`)를 열어 `data-reader-revision` 값을 확인하고, `origin/main`의 `website/content-manifest.json`에 적힌 그 장의 `revision`과 같은지 대조한다. 두 값이 같으면 `origin/main`의 내용이 배포에 반영된 것으로 본다. 다르면 배포가 늦거나 실패한 것이므로 그 사실과 두 값을 보고서에 적고, 차이 비교는 `origin/main`을 기준으로 하되 "배포 미반영" 상태를 함께 적는다. 확인한 URL과 시각을 기록한다.

리뷰 시작 시 기준 커밋이 `origin/main`의 후손인지도 확인한다(`git merge-base --is-ancestor origin/main <기준 커밋>`). 후손이 아니면 공개본에 이미 있는 변경이 기준 버전에 빠져 있거나 병합 충돌이 생길 수 있다. 이 경우 그 사실과 갈라진 커밋 목록을 P2 의견으로 적고, 공개 반영 전에 통합과 검사 재실행이 필요하다고 기록한다.

## 실행할 검사

다음 명령을 실행하고 결과를 보고서에 적는다. 출력은 실패·오류 행만 걸러서 기록한다. 실행하지 못한 검사는 이유와 함께 "실행하지 않음"으로 적고 통과로 쓰지 않는다.

| 명령(실행 위치) | 확인하는 것 |
|---|---|
| `python3 scripts/check_project.py` (루트) | 장·패턴·출처 수, JSON 유효성, 로컬 링크, 주장 메모의 출처 ID |
| `git diff --check <직전 공개 커밋>..<기준 커밋>` (루트) | 공개 이후 바뀐 파일의 공백 오류. 기준 버전은 커밋된 상태이므로 인자 없는 `git diff --check`는 아무것도 확인하지 않는다 |
| `npm test` (`website/`) | 출판 변환과 독서 기능의 단위 테스트 |
| `npm run check` (`website/`) | 콘텐츠 생성과 타입 검사 |
| `npm run build` (`website/`) | 프로덕션 빌드와 산출물 검사(`check-output.mjs`) |
| `npm run test:e2e` (`website/`) | 데스크톱·모바일 폭의 브라우저 읽기 흐름과 모바일 폭의 표 넘침 검사. Chromium 결과이며 실제 iOS Safari 결과와 구분한다 |
| 표 안의 가로 넘침 측정 (빌드 결과, 모바일 폭) | 대상 장의 본문 표마다 `scrollWidth`와 `clientWidth`를 측정한다. 표가 화면 폭 안에 들어가거나, 넘치는 표가 가로 스크롤되고 스크롤할 수 있다는 시각 단서를 가지는지 확인한다. 페이지 전체의 가로 넘침 검사는 표 내부의 잘림을 잡지 못하므로 이 측정을 따로 한다 |
| 링크 목적지의 내용 확인 (빌드 결과) | 대상 장의 내부 링크와 공개 경로로 변환된 링크를 표본으로 열어, 목적지가 링크 문장이 약속한 내용을 실제로 담는지 확인한다. 빌드의 링크·앵커 검사(`check-output.mjs`)는 목적지가 열리는지만 확인하므로 내용 확인을 대신하지 않는다 |

`npm ci`가 필요하면 먼저 실행한다. 네 축을 병렬로 리뷰할 때 출판 축은 `git worktree add <임시 경로> <기준 커밋>`으로 기준 커밋의 별도 사본을 만들고, 그 사본의 `website/`에서 `npm ci`와 빌드·테스트를 실행한다. 같은 작업 트리에서 빌드하면 다른 에이전트의 실행이 `dist/`와 `src/content/docs/`를 덮어써, 확인한 산출물이 기준 버전의 것인지 보장할 수 없기 때문이다. 리뷰를 마치면 `git worktree remove`로 사본을 지운다. 빌드 산출물(`dist/`, `src/content/docs/`, `src/data/book.json`)은 생성물이므로 커밋 대상으로 판정하지 않는다.

## 검토 기준

### 1. 원고와 공개본이 일치하는가

빌드한 페이지에서 대상 장의 제목·절 제목·표·직접 인용·출처 표식이 원고와 같은지 표본을 골라 확인한다. 공개본에서 본문이 잘리거나 표·인용이 깨지면 P0이다. 내부 파일 링크는 공개 경로로 변환되어야 하며, 등록하지 않은 내부 링크는 빌드를 실패시킨다. 본문이 인용한 출처만, 공개 필드만 발행되는지 확인한다. 내부 메모(`limit`, `usage_review` 등)가 공개되면 P1이다.

### 2. 마크다운이 의도대로 렌더링되는가

다음 문제는 원고에서 검색해 찾고 빌드 결과에서 확인한다. 범위 표기의 `~`가 같은 문단의 다른 `~`와 짝지어 취소선이 되는 문제는 `-`나 "약"으로 고치기를 제안한다. 닫는 `**` 바로 앞이 `)`·`」`·`%`·`.` 같은 문장부호이고 바로 뒤에 글자가 붙어 강조 기호가 그대로 노출되는 문제는 닫는 기호 뒤에 공백을 넣기를 제안한다. 의미를 가리는 렌더링 오류는 P1, 보기만 어색한 오류는 P2다.

### 3. 수정 표시와 앵커가 독자의 읽기를 보존하는가

의미가 바뀐 장은 `content-manifest.json`에서 해당 장의 `revision`을 올려야 한다. 그래야 이미 읽은 독자에게 "읽은 뒤 수정됨"이 표시된다. 오탈자 수정만으로는 올리지 않는다. 의미가 바뀌었는데 revision이 그대로이면 P1, 의미 변화가 없는데 올렸으면 P3이다. 기존 절의 앵커는 바뀌지 않아야 한다. 절 제목을 바꾸었다면 manifest에서 기존 앵커 ID가 새 제목에 이어지는지 확인한다. 기존 앵커가 사라져 외부 링크와 읽기 기록이 끊기면 P1이다.

### 4. 체인지 로그가 독자에게 필요한 변화를 알리는가

[체인지 로그 정책](../../skills/book-changelog/references/policy.md)의 기준 질문, 즉 "이 변경을 모르는 독자가 이해·적용·읽기에서 중요한 차이를 놓치는가"로 판단한다. 중심 주장·정의·적용 조건·책임·권한의 변경, 사실 정정, 증거의 철회나 확인 범위 축소, 라이선스·공개 범위의 변경이 기록되지 않았으면 P1이다. 의미가 바뀌어 revision을 올린 장은 체인지 로그 항목에서 그 장으로 가는 링크를 반드시 가져야 한다. 독자가 로그에서 바뀐 장을 찾아갈 수 있어야 하기 때문이다. 변화는 기록되었지만 해당 장으로 가는 링크가 없으면 P2다. 커밋 목록이나 내부 유지보수가 독자용 로그에 들어갔으면 P2다. 공개된 항목과 "공개 예정" 항목이 구분되는지, 공개 날짜를 배포 확인 전에 확정하지 않았는지 본다. 이미 공개한 중요한 이력이 삭제되면 P1이다.

### 5. 라이선스와 공개 상태가 정확한가

`LICENSE.md`는 책 콘텐츠에 CC BY-SA 4.0을, `website/` 코드에 MIT를 적용하고 제3자 자료를 제외한다. 공개본의 라이선스 표시가 이 구분과 다르거나, 제3자 자료(인용 원문, 이미지)를 CC BY-SA로 재허락하는 것처럼 보이면 P0이다. 공개본의 상태 표시가 `book-publication.json`의 `status_label`("공개 초안")과 일치하는지, 편집 확정 전인데 완성본처럼 표시하지 않는지 확인한다. 피드백 경로(GitHub Issues)가 공개 접근 가능한지 확인한다.

### 6. 메타데이터가 서로 맞는가

책 제목·부제·저자, 장·패턴의 수와 제목, 집필 상태가 `book_project.json`, `outline/toc.md`, `README.md`, `STATUS.md`, 웹 메타데이터 사이에서 일치하는지 확인한다. 리뷰나 수정 결과로 집필 상태가 임의로 올라가 있으면 P1이다. 공유 썸네일과 페이지 제목에 이전 제목이나 IDD 중심 표현이 남아 있으면 P2다.

### 7. 독자가 읽을 수 있는가

모바일 폭에서 표가 가로로 넘쳐 내용이 가려지지 않는지("실행할 검사"의 표 넘침 측정으로 판정한다. 넘치는 표가 가로 스크롤되더라도 스크롤 단서가 없어 열이 잘린 것처럼 보이면 의견으로 기록한다), 제목 구조가 건너뛰지 않는지(h2 다음 h4 등), 이미지에 대체 텍스트가 있는지, 링크 텍스트가 목적지를 알려 주는지, 목적지가 링크 문장이 약속한 내용을 담는지 확인한다. 본문을 읽을 수 없게 만드는 문제는 P1, 불편을 주는 문제는 P2다.

### 8. 독자 본문에 제작 정보가 새지 않는가

"초고", "검토 대기", 결정 번호(D18 등), 세션 기록, 리뷰 의견 ID, `TODO` 같은 제작 정보가 공개 본문에 노출되었는지 검색한다. 독자에게 공개 초안임을 알리는 의도된 표시는 제외한다.

| 검사 | 결과(통과·실패·실행하지 않음) | 실패 내용 요약 |
|---|---|---|

표 아래에 revision을 올려야 하는 장, 체인지 로그에 추가해야 하는 항목, 사라진 앵커를 목록으로 적는다.

## 하지 않는 일

커밋·푸시·배포를 하지 않는다. `content-manifest.json`, `CHANGELOG.md`, 메타데이터를 직접 고치지 않고 수정안만 낸다. 배포 사이트의 실제 상태를 확인했다면 확인한 URL과 시각을 적고, 로컬 빌드 결과와 구분한다. 로컬 빌드 통과를 배포 성공으로 보고하지 않는다.
