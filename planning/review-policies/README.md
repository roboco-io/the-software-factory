## 왜 네 개의 정책으로 나누는가

이 책의 리뷰는 서로 다른 질문에 답한다. 논증이 성립하는가, 근거가 그 논증을 지지하는가, 리더 독자가 그 논증을 이해하는가, 공개본이 원고를 손상 없이 전달하는가. 한 리뷰어가 네 질문을 함께 다루면 쉽게 보이는 문체 문제가 의견을 채우고 근거의 빈틈과 논증의 모순이 덜 보인다. 그래서 질문마다 별도의 정책과 리뷰 에이전트를 두고, 각 리뷰는 자기 축의 판정만 내린다.

| 축 | 정책 | 핵심 질문 | 리뷰 에이전트 |
|---|---|---|---|
| 1. 논증·구조 | [01-argument.md](01-argument.md) | 리더가 내릴 결정과 그 이유가 장·부·책 전체에서 일관되게 성립하는가 | `review-argument` |
| 2. 사실·출처 | [02-evidence.md](02-evidence.md) | 각 주장이 출처가 실제로 말하는 범위 안에 있는가 | `review-evidence` |
| 3. 독자·문체 | [03-reader-style.md](03-reader-style.md) | 기술·비기술 리더가 저자의 추가 설명 없이 판단을 재구성할 수 있는가 | `review-reader-style` |
| 4. 출판 준비 | [04-publication.md](04-publication.md) | 공개 웹본·메타데이터·라이선스·변경 기록이 원고와 일치하고 독자의 읽기를 보장하는가 | `review-publication` |

축을 나눈다고 해서 다른 축의 문제를 숨기지 않는다. 리뷰어가 자기 축 밖의 문제를 발견하면 보고서의 "다른 축으로 넘길 사항"에 위치와 이유만 적고 판정하지 않는다. 해당 축의 리뷰가 그 사항을 받아 판정한다.

## 실행 순서

네 리뷰는 같은 기준 버전에 대해 병렬로 실행할 수 있다. 다만 수정은 1 → 2 → 3 → 4 순서로 반영한다. 논증 수정이 주장을 바꾸면 그 주장의 근거 판정이 무효가 되고, 근거 수정이 표현을 좁히면 문체 판정이 무효가 되며, 원고가 바뀌면 공개본 판정도 다시 해야 하기 때문이다. 앞 축의 수정이 뒤 축의 판정 대상 문단을 바꾸었다면 뒤 축의 해당 의견은 "재검토 필요"로 돌린다.

책 전체를 처음 리뷰할 때는 1·7·9·16·17장을 먼저 검토한다. 이 다섯 장은 각각 책의 약속, 수용 판정, 운영 책임, 인간의 역할, 성과 측정을 담당하므로 여기서 기준과 용어를 맞춘 뒤 나머지 장과 15개 패턴으로 넓힌다. 사용자가 특정 장이나 축을 지정하면 그 범위를 따른다.

## 모든 축에 공통으로 적용하는 규칙

**기준 버전을 고정한다.** 리뷰 시작 시 `git rev-parse HEAD`와 작업 트리 상태를 기록한다. 대상 파일에 커밋하지 않은 변경이 있으면 각 파일의 SHA-256을 매니페스트에 남긴다. 의견은 이 버전에 대해서만 유효하다. 이전 버전의 판정을 새 변경에 자동으로 적용하지 않는다.

**리뷰는 읽기 전용이다.** 리뷰 에이전트는 원고·패턴·카탈로그·출처 대장·주장 메모·웹 소스를 수정하지 않고, 자기 보고서와 매니페스트만 쓴다. 네 에이전트가 병렬로 실행될 때 같은 파일을 동시에 고치는 충돌을 막고, 판정과 수정을 분리하기 위해서다. 수정은 사용자가 별도로 지시한 뒤 수행하며, 수정 후에는 해당 축의 리뷰어가 수용 조건을 다시 확인한다. 커밋·푸시·배포·편집 확정은 리뷰 범위에 포함하지 않는다.

**실제로 한 확인만 보고한다.** 읽은 파일과 범위, 접근하지 못한 자료, 실행한 명령과 결과를 구분해 적는다. 일부만 읽었다면 그 범위를 적는다. 문제를 찾지 못했다면 의견을 만들어내지 않고 "이 범위에서 해당 문제를 발견하지 않았다"와 남은 불확실성을 적는다. AI가 생성한 독자 반응을 실제 독자 시험으로, 같은 AI의 재검토나 다른 모델의 사용을 독립 리뷰로 표시하지 않는다.

**자동 검사와 리뷰 판정을 구분한다.** `scripts/check_project.py`와 웹 테스트·빌드는 JSON·링크·ID·형식을 확인한다. 이 검사의 통과는 사실·인과·논증·독자 이해의 승인이 아니다.

### 우선순위

| 등급 | 기준 | 처리 |
|---|---|---|
| P0 | 만들어낸 사례·인용·수치, 중대한 사실 오류, 확인 범위를 넘긴 성과·권리 주장, 독자에게 공개된 잘못된 내용이나 접근 불가 | 해결 전에는 공개 범위 확대와 편집 확정을 보류한다 |
| P1 | 중심 논증의 모순·누락, 패턴 의미의 변형, 결정·작동 원리·비용·한계의 불명확, 출처가 지지하지 않는 핵심 주장 | 해당 장을 수정하고 수용 조건을 확인한 뒤 닫는다 |
| P2 | 이해를 막는 용어·반복·문단 연결, 근거 기록의 누락, 렌더링·메타데이터의 부분 오류 | 수정하거나 수정하지 않는 이유를 기록한다 |
| P3 | 선택 가능한 구성·표현·예시 제안 | 저자가 채택 여부를 정한다 |

취향 차이를 P0이나 P1로 올리지 않는다. 오탈자라도 주체·수치·의미를 바꾸면 등급을 올린다. 점수 합산으로 필수 문제를 상쇄하지 않는다.

### 의견의 형식

의견 ID는 축 접두어와 번호로 쓴다: 논증 `A001`, 근거 `E001`, 독자·문체 `R001`, 출판 `U001`. 각 의견에는 다음을 적는다.

| 필드 | 내용 |
|---|---|
| ID / 우선순위 / 상태 | 예: `E003 / P1 / 열림` |
| 위치 / 버전 | 파일·절 제목·문단(또는 행)과 기준 버전 |
| 문제 / 독자 영향 | 무엇이 잘못되었고, 그 때문에 리더 독자의 어떤 판단이 틀리거나 불가능해지는가 |
| 근거 / 확인 수준 | 정책의 어느 기준에 해당하는지, 실제로 읽거나 실행한 것, 확인하지 못한 것 |
| 최소 수정 | 문제를 해소하는 가장 작은 변경. 근거 확보·주장 축소·제안 표시·삭제·구조 보강 중 하나 이상 |
| 수용 조건 | 수정 후 무엇을 읽거나 실행하면 이 의견을 닫을 수 있는가 |

"더 구체적으로 써라"처럼 위치와 부족한 판단을 알 수 없는 의견은 쓰지 않는다.

### 의견의 상태

`열림` → `수정됨·검증 대기` → `검증 완료`의 순서로 진행한다. 수정자가 수정했다고 선언한 것만으로 닫지 않는다. 해당 축의 리뷰어가 수정본을 읽고 수용 조건과 새 모순이 없는지 확인해야 `검증 완료`가 된다. 근거와 선택지를 정리했지만 저자의 결정이 필요한 의견은 `저자 판단 대기`, 저자가 채택하지 않은 의견은 `채택하지 않음`과 이유를 남긴다. 앞 축의 수정으로 대상 문단이 바뀐 의견은 `재검토 필요`로 둔다.

## 보고서와 기록

보고서는 `planning/reviews/YYYY-MM-DD-<축>-<범위>.md`에, 의견의 구조화 대장은 같은 이름의 `.json`에, 기준 버전과 파일 해시는 `-manifest.json`에 저장한다. 축 이름은 `argument`, `evidence`, `reader-style`, `publication`을 쓴다. 범위는 `book`, `ch07`, `ch01-05`, `p03`처럼 쓴다.

보고서는 다음 순서를 따른다. (1) 범위: 적용 정책, 기준 버전, 실제로 읽거나 실행한 것, 확인하지 못한 것. (2) 축별 요약: 각 정책이 요구하는 요약표. (3) 의견: 우선순위가 높은 것부터. (4) 다른 축으로 넘길 사항. (5) 판정과 인계: 남은 P0·P1, 수행하지 않은 확인, 다음 작업.

리뷰를 마치면 `STATUS.md`에 날짜, 축, 범위, 보고서 경로, 남은 P0·P1의 수를 짧게 남긴다. 리뷰 결과로 원고의 집필 상태를 올리지 않는다. 편집 확정은 지정 버전에서 네 축의 P0·P1이 모두 `검증 완료`이고 P2의 처리 이유가 기록되었으며 저자가 실제로 승인했을 때만 기록한다.

## 에이전트로 리뷰하기

Claude Code에서는 `.claude/agents/`의 네 리뷰 에이전트를 사용한다. 예를 들어 "review-argument 에이전트로 7장을 리뷰해줘" 또는 "네 리뷰 에이전트로 9장을 병렬 리뷰해줘"처럼 요청한다. 각 에이전트는 자기 정책과 이 문서를 먼저 읽고, 위 형식으로 보고서를 저장한 뒤 요약만 돌려준다. 다른 클라이언트에서는 [idd-manuscript-review 스킬](../../skills/idd-manuscript-review/SKILL.md)에 축을 지정해 같은 정책을 적용한다.
