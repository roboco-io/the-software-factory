# 출판 축 규칙 구조화 설계(시범)

- 상태: 설계 검토 중(2026-10-16). 구현 전.
- 범위: [출판 준비 리뷰 정책](04-publication.md)의 기준 가운데 프로그램이 판정할 수 있는 기준.
- 관련 문서: [리뷰 공통 규칙](README.md), [리뷰 프로세스](process.md)

## 1. 배경과 목적

리뷰 정책 네 개는 모두 문장으로 쓰여 있다. 리뷰 에이전트는 이 문장을 읽고 판단한다. 그런데 출판 축의 기준 상당수는 판단이 필요하지 않은 기계적 검사다. 범위 표기의 `~`, 체인지 로그의 장 링크 누락, 기준 커밋의 후손 관계 같은 것들이다. 이런 기준을 에이전트가 매번 문장에서 해석해 직접 검색하면 세 가지 문제가 생긴다. 같은 원고를 다시 리뷰해도 결과가 달라질 수 있다. 7장 시범에서 같은 모델을 다시 돌렸을 때 P1과 P2의 경계가 흔들렸다. 에이전트의 토큰이 단순 검색에 쓰인다. 배포 전에 자동으로 막을 수 없다.

이 설계는 그런 기준을 YAML 규칙 등록부와 검사 스크립트로 옮긴다. 목적은 세 가지다. 같은 입력에 같은 결과를 내고, 일부 규칙은 CI에서 배포를 막고, 리뷰 에이전트가 판단이 필요한 기준에 집중하게 한다. 이번 범위는 출판 축 하나의 시범이다. 효과가 확인되면 공통 스키마와 용어집 규칙, 다른 축의 기계적 기준으로 넓힌다. 확대는 이 설계의 범위가 아니다.

## 2. 결정된 사항

다음 사항은 저자가 2026-10-16 대화에서 정했다.

| 항목 | 결정 |
|---|---|
| 검사 결과의 용도 | 리뷰 도구로 쓰고, 오판 가능성이 낮은 일부 규칙만 CI에서 배포를 막는다 |
| 형식 | YAML. `PyYAML`을 프로젝트 의존성으로 추가한다 |
| 구조 | 규칙 등록부(YAML)와 이름 붙은 검사 함수(Python). 범용 규칙 엔진은 만들지 않는다 |

범용 규칙 엔진을 택하지 않은 이유는 다음과 같다. revision 증가나 체인지 로그 링크 같은 규칙은 선언만으로 표현하기 어렵다. 이런 규칙까지 엔진으로 처리하려 하면 YAML이 작은 프로그래밍 언어로 변한다. 시범의 목적은 효과 확인이므로 그 비용을 들이지 않는다.

## 3. 파일 구성

| 파일 | 역할 |
|---|---|
| `planning/review-policies/rules/publication.yaml` | 출판 축 규칙 등록부. 기계가 판정하는 규칙의 원본이다 |
| `scripts/review_checks.py` | 등록부를 읽어 검사를 실행하고 의견 후보를 낸다 |
| `scripts/tests/test_review_checks.py` | 검사 함수와 등록부의 단위 테스트 |
| `requirements.txt` | `PyYAML` 고정 버전 |
| `planning/review-policies/04-publication.md`(수정) | 기계 판정으로 옮긴 기준은 규칙 ID와 존재 이유만 남긴다 |
| `.claude/agents/review-publication.md`(수정) | 리뷰 시작 시 리뷰 모드를 실행하고 후보를 처리하는 절차를 넣는다 |
| `.github/workflows/pages.yml`(수정) | 의존성 설치 뒤 `review_checks.py --gate`를 실행한다 |

`scripts/check_project.py`는 고치지 않는다. 이 스크립트는 저장소 구조의 무결성(장·패턴·출처 수, JSON 유효성, 로컬 링크)을 검사한다. 새 스크립트는 리뷰 정책의 규칙을 검사한다. 두 스크립트의 책임이 다르므로 분리한다.

같은 규칙을 YAML과 정책 문장 두 곳에 함께 적지 않는다. 두 곳에 적으면 한쪽만 고쳐져 어긋나기 때문이다. 기계 판정 규칙의 원본은 YAML이다. 정책 문서는 규칙 ID를 참조하고 그 규칙이 왜 있는지만 설명한다.

## 4. 등록부 스키마

```yaml
version: 1
axis: publication
id_prefix: U
note: >
  이 목록은 기계가 판정할 수 있는 규칙이다. 리뷰 범위의 전부가 아니다.
  나머지 기준은 04-publication.md를 따른다.
rules:
  - id: PUB-001
    title: 범위 표기의 물결표
    priority: P3
    mode: gate
    check: tilde_range
    scope: published_text
    params: {}
    exceptions: []
    policy_ref: "04-publication.md#2-마크다운이-의도대로-렌더링되는가"
    needs_judgment: false
    fix: "범위는 `-`, 근사는 `약`으로 쓴다."
```

| 필드 | 뜻 |
|---|---|
| `id` | 규칙 ID. 의견 ID(U001 등)와 다르다 |
| `priority` | 공통 README의 P0-P3. 검사 함수가 조건에 따라 올릴 수 있으며, 그 조건은 함수 설명에 적는다 |
| `mode` | `gate`는 CI에서 배포를 막는다. `review`는 리뷰 모드에서만 후보를 낸다 |
| `check` | `review_checks.py`의 검사 함수 이름 |
| `scope` | `published_text`(공개 변환 뒤 본문, 코드 구간 제외), `manifest`, `changelog`, `git` 중 하나 |
| `exceptions` | 예외로 둘 `path`, `line`, `reason`의 목록. `reason`이 비어 있으면 설정 오류다 |
| `policy_ref` | 정책 문서에서 이 규칙의 근거가 있는 절 |
| `needs_judgment` | true면 후보를 확정 의견이 아니라 리뷰어 확인 대상으로 낸다 |
| `fix` | 최소 수정안의 기본 문장 |

`note` 필드는 에이전트가 이 목록을 리뷰 범위의 전부로 읽지 않게 하려고 둔다. 용어집에 "닫힌 목록이 아니다"라고 적은 것과 같은 이유다.

`published_text`는 원고 원문이 아니라 공개 변환을 거친 뒤의 본문이다. 이렇게 정한 이유는 다음과 같다. 패턴 카드 p03, p07, p13의 3행에는 "상태: 초고 · 저자 검토 대기"가 있다. 그런데 이 줄은 공개 변환에서 삭제되어 독자에게 보이지 않는다(`website/scripts/publication.mjs:23`). 원문을 검사하면 이 줄이 위반으로 잡힌다. 스크립트는 같은 변환 규칙(제목 줄과 `상태:` 줄 삭제)을 Python으로 재현한다. 두 구현이 어긋날 위험은 6절의 테스트로 확인한다.

## 5. 시범 규칙

| ID | 규칙 | 등급 | 모드 | 판단 필요 |
|---|---|---|---|---|
| PUB-001 | 범위 표기의 `~`(숫자 사이의 `~`) | P3. 같은 문단에 `~`가 두 개 이상이면 P2 | gate | 아니오 |
| PUB-002 | 닫는 `**`나 `*` 바로 앞이 문장부호(`)`, `」`, `%`, `.` 등)이고 바로 뒤에 글자가 붙음 | P1 | gate | 아니오 |
| PUB-003 | 공개 본문의 제작 정보. 결정 번호(`D` 뒤에 숫자), `TODO`, 리뷰 의견 ID(`[AERUN]` 뒤에 숫자 세 자리), 상태 표기 "초고" | P1 | gate | 아니오 |
| PUB-004 | 기준 커밋이 `origin/main`의 후손이 아님 | P2 | review | 아니오 |
| PUB-005 | 기준 버전 이후 원고가 바뀌었는데 manifest의 revision이 그대로인 장·패턴 | P1 | review | 예 |
| PUB-006 | revision이 올라간 장·패턴으로 가는 링크가 체인지 로그에 없음 | P2 | review | 아니오 |
| PUB-007 | 기준 버전 manifest에 있던 앵커가 현재 manifest에서 사라짐 | P1 | review | 아니오 |

PUB-001의 등급은 지난 리뷰의 판정과 정책 문장을 함께 고려해 정했다. 1·9·16·17장 라운드의 U006은 한 문단에 `~`가 하나뿐이어서 취소선으로 렌더링되지 않는 경우를 P3로 판정했다. 같은 문단에 `~`가 둘 이상이면 실제로 취소선이 될 수 있으므로 정책의 "보기만 어색한 오류"에 해당하는 P2로 올린다. 의미를 가리는지는 기계가 판단할 수 없으므로 P1로 올리지 않는다. P1이 필요하면 리뷰어가 이유를 적고 올린다. 등급이 P3인데도 차단하는 이유는 전역 작성 규칙이 범위 표기의 `~`를 조건 없이 금지하고, 숫자 사이의 `~`는 오탐 가능성이 낮기 때문이다.

PUB-003은 낱말 "검토 대기"를 검사하지 않는다. p07의 11행과 27행 본문이 이 낱말을 정상적인 뜻으로 쓰기 때문이다. 공개 초안임을 알리는 의도된 표시(`book-publication.json`의 `status_label`)는 공개 본문에 없으므로 이 검사와 겹치지 않는다. 다만 구현할 때 실제로 겹치지 않는지 확인한다.

PUB-005는 판단이 필요하다. 정책은 의미가 바뀐 경우에만 revision을 올리고 오탈자 수정만으로는 올리지 않는다고 정한다. 프로그램은 원고가 바뀌었다는 사실만 알 수 있다. 그래서 후보에 바뀐 행 수와 diff 요약을 붙이고, 의미가 바뀌었는지는 리뷰어가 판정한다.

PUB-004부터 PUB-007까지는 기준 버전과 비교해야 판정할 수 있어 리뷰 모드에서만 실행한다. PUB-006은 장(`/book/chNN/`)뿐 아니라 패턴 카드 링크도 대상으로 한다. 7장 검증 라운드의 U004가 p06·p07의 revision을 올렸는데 패턴 링크가 없던 사례이기 때문이다. PUB-006은 체인지 로그의 "공개 예정" 항목과 기준 버전 이후 추가된 날짜 항목을 검사 대상으로 삼는다.

다음 기준은 YAML로 옮기지 않는다. 빌드·테스트 명령 목록은 CI가 이미 실행한다. 표 넘침 측정, 링크 목적지의 내용 확인, 라이선스 판단, 메타데이터 일관성, 체인지 로그 서술의 적절성은 판단이 필요하다. `git diff --check`(지난 라운드 U008)는 시범 뒤 추가를 검토한다.

현재 원고에는 PUB-001 위반이 한 곳 있다. 18장 23행의 `5~7월`이다. 이 행을 `5-7월`로 고치는 작업을 구현 범위에 넣는다. 고치지 않으면 CI 차단이 도입과 동시에 배포를 막는다. 이 수정은 의미 변화가 없으므로 revision을 올리지 않는다.

## 6. 스크립트 동작

### 실행 모드

| 모드 | 명령 | 동작 |
|---|---|---|
| CI 차단 | `python3 scripts/review_checks.py --gate` | `mode: gate` 규칙만 현재 작업 트리에 실행한다. 위반이 있으면 종료 코드 1 |
| 리뷰 | `python3 scripts/review_checks.py --base <직전 공개 커밋> --out <경로>.json` | 모든 규칙을 실행하고 의견 후보를 파일로 쓴다. 위반이 있어도 종료 코드 0 |

`--base`가 없으면 리뷰 모드는 비교 규칙(PUB-004부터 PUB-007까지)을 "실행하지 않음"으로 기록한다. 통과로 기록하지 않는다. 정책의 "실행하지 못한 검사는 통과로 쓰지 않는다" 규칙을 따른 것이다.

### 의견 후보 형식

후보는 공통 README의 JSON 스키마 필드를 따른다. 채우는 필드는 `rule_id`, `priority`, `status`(항상 `열림`), `axis`, `location`(파일:행), `version`(기준 커밋과 현재 커밋), `problem`, `evidence`(일치한 원문 구간), `minimal_fix`, `needs_judgment`다. `id`는 비워 둔다. 리뷰어가 후보를 의견으로 채택할 때 ID를 붙인다. 프로그램이 ID를 매기면 리뷰어가 버린 후보 때문에 번호가 비기 때문이다. 파일 머리에는 실행한 규칙 ID, 실행하지 않은 규칙과 그 이유, 등록부 버전을 적는다.

### 설정 오류

다음 경우는 위반과 구분해 종료 코드 2를 돌려준다. YAML 문법 오류, 필수 필드 누락, 존재하지 않는 검사 함수 이름, `reason`이 빈 예외가 여기에 해당한다. CI에서는 종료 코드 2도 배포를 막는다. 규칙이 조용히 꺼진 채 통과하는 일을 막기 위해서다.

## 7. 에이전트 연동

출판 축 에이전트 정의와 `04-publication.md`의 "실행할 검사"에 다음 절차를 넣는다. 리뷰를 시작할 때 리뷰 모드를 실행하고, 후보를 다음 기준으로 처리한다.

`needs_judgment: false`인 후보는 그대로 의견으로 옮긴다. 등급을 바꾸면 바꾼 이유를 의견에 적는다. `needs_judgment: true`인 후보는 원문을 읽고 채택 여부를 판정한다. 보고서에는 실행한 규칙 ID, 채택하지 않은 후보와 그 이유를 적는다.

정책 문서에서 기계 판정으로 옮긴 기준은 문장을 줄인다. 그 자리에는 "PUB-001이 판정한다"와 그 규칙이 있는 이유를 남긴다. 판단이 필요한 기준의 문장은 바꾸지 않는다. 에이전트가 규칙 목록만 보고 리뷰를 끝내지 않도록, 정책 문서에도 "기계 규칙은 리뷰 범위의 일부"라는 문장을 둔다.

## 8. 테스트

`scripts/tests/test_review_checks.py`는 기존 `test_demo_examples.py`와 같은 방식으로 작성하며, 다음을 확인한다.

1. 각 검사 함수가 위반 예시는 잡고 정상 예시는 통과시킨다. 정상 예시에는 p07 본문의 "검토 대기", 코드 구간 안의 `~`, `상태:` 줄이 들어간다.
2. 등록부의 모든 규칙이 필수 필드를 갖추고 실제 함수를 가리킨다.
3. `policy_ref`가 가리키는 정책 문서의 절 제목이 실제로 있다.
4. Python의 공개 변환 재현이 `publication.mjs`의 결과와 같다. 대표 원고 파일 몇 개를 두 구현에 넣어 결과를 비교한다.
5. 설정 오류가 종료 코드 2를 낸다.

CI는 `pip install -r requirements.txt` 뒤 단위 테스트와 `--gate`를 실행한다.

## 9. 시범 성공 기준

다음 세 가지가 충족되면 시범이 끝난 것으로 본다.

1. 18장 23행을 고친 뒤 현재 `main`에서 `--gate`가 통과하고, CI가 이를 실행한다.
2. 과거 라운드의 기준 커밋을 `--base`로 넣고 실행하면 그 라운드의 출판 축 의견 가운데 규칙 대상인 것이 후보로 다시 나온다. 대상은 7장 라운드 U003(체인지 로그에 7장 링크 없음), 7장 검증 라운드 U004(p06·p07 링크 없음), 1·9·16·17장 라운드 U004(후손 아님)와 U006(물결표)이다. 재현되지 않는 의견이 있으면 그 원인을 규칙의 결함으로 보고 고친다. 원인이 과거 상태를 복원할 수 없는 데 있다면 그 사실을 기록한다.
