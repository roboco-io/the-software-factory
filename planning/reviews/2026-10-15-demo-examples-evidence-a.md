## 버전 차이

GitHub compare는 후보가 이전보다 3커밋 앞서며 총 25파일 차이를 보고했다. 담당 중핵인 위험 정책·분류·gate·요청 템플릿·triage·evidence·guard·command·상태 전이와 관련 기존 테스트·CI는 compare 변경 목록에 없고, 기존 조사 목록과 대조 가능한 파일의 blob SHA도 같다. 이 부분의 운영 의미가 바뀌었다는 근거는 발견하지 못했다.

README는 비개발자용 흐름과 책의 관계 설명으로 재편됐다. 상세 설정·운영·보안 한계는 새 `docs/operations.md`로 분리됐다. 이전 README에서 준비 실패 수동 복구, 증거 판정 조작 한계, 단독 CODEOWNER 한계를 확인하고 후보 operations의 해당 절과 대조했다. 따라서 현재 버전을 설명하며 “README가 밝힌다”라고 쓰는 7·8·12장은 “운영 안내가 밝힌다”로 바꾸거나 고정된 옛 README 사례임을 유지해야 한다. 오래된 코드 링크 자체가 틀린 근거는 아니다.

## 사례별 정적 사실과 권장 배치

### A01: 요청 정리와 실행 승인을 나눈다 — 5장 / S61

- 기능 요청서는 목표와 수용 기준을 필수 입력으로 받는다.
- triage 프롬프트는 파일 변경을 금지하고 종류·중복·예상 위험·수용 기준·요약의 구조화된 출력을 요구한다.
- triage 코드는 읽기 전용 수행을 요청하고 스키마로 출력 형태를 검사한 뒤 댓글·라벨을 게시한다. 예상 위험은 실제 변경 파일의 최종 등급과 다르다.
- 상태 기계에서 triage는 새 요청을 정리 상태로 보낼 수 있지만 승인 상태로 바꾸는 주체는 command다.
- command는 저장소 write/maintain/admin 권한을 확인한다. 정상 신규 요청은 정리 뒤 쓰기 권한자의 시작 판단을 거친다. 다만 코드상 new → approved 직접 전이도 있으므로 “모든 작업에 triage 완료가 강제된다”라고 쓰면 안 된다.
- 본문 제안: “목표와 수용 기준을 먼저 받되, 에이전트가 이를 정리하는 일과 작업 시작을 허용하는 일을 나눈다. 리더는 정리 결과의 형식 충족과 목표의 타당성을 구분한다.”
- 여러 파일의 관계가 핵심이므로 독자 해설 ‘요청에서 실행 승인까지’ 권장. 기능 요청서 → triage 지침/단계 → 상태 기계/명령 순으로 안내한다.
- 한계: 스키마는 사업적 적절성을 검증하지 않는다. readOnly 설정이 모든 환경에서 실제 강제된다는 확인도 이번 범위 밖이다.

### A02: 변경 위험이 수용 권한을 바꾼다 — 3·12장 / S60

- 위험 정책은 경로별 규칙과 필수 체크 목록을 선언한다. 파일별 첫 일치 규칙을 쓰고 PR은 변경 파일 중 가장 높은 등급을 쓴다. 미일치 기본 등급은 T2다.
- 팩토리 자체 코드·지침·워크플로 등은 T3, 일반 문서 등은 T0, 일부 제품 코드는 T1, 인증·마이그레이션 등은 T2다. 이름 변경은 이전/새 경로 모두 반영한다.
- gate는 팩토리 봇이 연 대상 PR인지와 연결 이슈 상태를 확인한 뒤 현재 head의 체크와 판정을 읽는다.
- T1은 현재 head에 대응하는 승인 판정이 필요하다. 승인 표식의 SHA뿐 아니라 GitHub 리뷰 commitId도 일치해야 한다. T0은 승인 없이도 갈 수 있지만 REQUEST_CHANGES는 무시하지 않는다.
- T2·T3는 사람 이관 상태로 보내 자동 병합하지 않는다. 개선 PR은 별도 경로로 자동 병합 대상에서 제외한다.
- 파일 목록을 완전히 얻지 못하거나 위험 판정에 실패하면 자동 병합을 막는다. 병합 요청에도 읽은 head SHA를 전달한다.
- 본문 제안: 3장은 “변경 대상에 따라 위임 경계를 달리한다”에 집중하고, 12장은 “같은 버전의 증거로 반영 권한을 행사한다”에 집중한다. 동일 데모 소개를 반복하지 않는다.
- 독자 해설 ‘위험과 반영 권한’에 정책 → 경로 분류 → 현재 버전 판정 → 자동 병합/사람 이관을 모은다.
- 한계: T0–T3는 위험 등급이지 책의 정책 적용 범위 계층이 아니다. 정책 계층·최상위 원칙 전체가 구현됐다고 소급하지 않는다. gate의 체크 판정은 success뿐 아니라 skipped/neutral도 pass로 처리하므로 “필수 검사 모두 실제 실행됨”을 보장한다고 쓰지 않는다.
- 운영 안내는 유일한 CODEOWNER가 직접 작성한 PR에는 승인이 강제되지 않는 한계를 명시한다. 코드상 자동 병합 거부와 전체 저장소 보호는 구분한다.

### A03: 실패의 종류까지 따져 수정 증거를 만든다 — 7장 / S62

- evidence-plan은 봇 PR과 메타, 연결 이슈의 bug 라벨로 대상 여부를 정한다. head가 바뀌거나 파일 목록을 확정할 수 없으면 그 불확실성을 계획에 남긴다.
- 적용 대상이면 PR이 추가·수정한 테스트 파일을 수정 전 base 트리에 덮어써 비교하고, 같은 테스트를 head에서도 판정한다.
- 수정 전의 개별 단언 실패와 수정 후 통과를 요구한다. 보고서 누락·잘못된 형식·수집 오류·시간 초과·미수집을 재현 성공으로 인정하지 않는다.
- API/web/factory의 Vitest 테스트를 실행 대상으로 정하며 Playwright 브라우저 E2E는 이 판정에서 실행하지 않는다. 비대상 PR은 실행 없이 통과할 수 있다.
- CI는 base 버전 CLI가 계획과 판정을 수행하도록 정의한다. PR 코드는 evidence job에서 수행되며 명시적인 GitHub 토큰/시크릿 env를 넘기지 않는다. 이는 job 정의의 정적 확인이고 runner 전체의 침해 가능성이 없다는 검증이 아니다.
- 관련 테스트에서 base 단언 실패/head 통과, base 수집 오류, 보고서 누락, 다른 파일의 부분 문자열 매칭을 거부하는 단언을 선별 확인했다. 실행하지 않았다.
- 본문 제안: “검사 실패라는 표시에 그치지 않고, 수정이 없을 때 어떤 현상이 실패해야 하는지 정한다. 실행 자체가 실패한 경우는 버그를 재현한 증거와 구분한다.”
- 독자 해설 ‘수정 전후의 증거’에 대상 분류 → 테스트 전달 → 두 버전 비교 → 보고서 판정을 모은다.
- 한계: 운영 안내는 테스트와 판정이 같은 VM에서 돌고 JSON 보고서를 PR 코드가 위조할 수 있다고 명시한다. 악의적 작성자 차단 보장으로 쓰지 않는다.

### A04: 새 작업 중단과 개별 취소·복구를 나눈다 — 8장 / S63

- guard는 최근7일 implement/fix 실행을 집계해 10회 이상에서 성공률50% 미만이면 FACTORY_PAUSED를 켜고 알림을 남긴다. 기준값은 데모 설정이며 조직 표준이 아니다.
- 알림은 implement/fix 시작은 멈추되 triage·리뷰 기록·병합 판단·배포 반영은 계속됨을 설명한다. 실제 전체 경로 강제 확인은 담당 범위의 모든 caller를 실행한 것이 아니다.
- 사람이 pause를 풀면 PR이 없고 승인된 이슈를 일일 한도 안에서 다시 dispatch한다. 오래된 모든 작업의 자동 복구는 아니다.
- command는 권한과 현재 상태를 확인하고 stop 허용 상태이면 관련 실행 취소를 요청한 뒤 needs-human으로 옮긴다. retry/go도 허용 전이를 따라야 한다.
- 상태 기계에서 in-progress → approved 직접 전이는 없다. 운영 안내는 prepare 실패로 in-progress에 남은 작업을 사람이 stop 후 retry해야 하며 guard가 자동 복구하지 않음을 밝힌다.
- 본문 제안: “새 일을 더 받지 않는 판단, 진행 중 실행을 취소하는 판단, 이미 생긴 외부 효과를 복구하는 판단을 나눈다.”
- 독자 해설 ‘중단과 재개’에 실행 기록 → 차단기 → 운영자 해제와 개별 명령 → 상태 전이를 나란히 연결한다.
- 한계: 취소 API 요청이 외부 효과를 되돌리지는 않는다. 차단기 임계값의 통계 타당성·운영성과는 검증하지 않았다.

## 이용 조건 확인

후보 LICENSE 전체는 Apache License 2.0이다. 후보 README는 자체 코드·문서·설정에 적용된다고 명시한다. 원문의 2조는 복제·수정·배포 등을 허용하고 4조는 재배포 시 라이선스와 관련 고지 보존·수정 표시·해당 NOTICE 처리 조건을 둔다. 6조는 일반적 상표 사용권을 주지 않는다. 이 기록은 원문에서 확인한 조건이며 별도 법률 판단은 아니다.

THIRD_PARTY_LICENSES는 공식 RealWorld Hurl 테스트의 MIT 고지를 보존하며 프레임워크 로고를 별도 취급한다. 이번 해설은 자체 산문과 원문 링크로 작성할 수 있으므로 코드·설정 전문이나 이미지 복제는 필요하지 않다. 별도 NOTICE 존재 여부와 로고 이용 범위는 이번 점검에서 확인하지 않았다. 코드를 복제하기로 범위를 넓히면 추가 확인해야 한다.

## 미해결·검증 수용 기준

접근 실패는 없었다. 핵심 코드 의미 변경도 발견하지 못했다. 독자에게 달라질 주요 사항은 원문 접근 경로와 해설의 관계 설명이다.

1. 5장 해설이 triage와 승인을 나누되 모든 요청에 triage 선행이 강제된다고 쓰지 않는다.
2. 3·12장 해설은 위험 등급과 정책 계층을 혼동하지 않고 현재 head 판정을 설명한다.
3. 7장 해설은 단언 실패/수집 오류와 비대상 통과를 구분하며 악의적 판정 조작 한계를 보존한다.
4. 8장 해설은 pause/stop/retry/외부 효과 복구를 구분하고 준비 실패의 수동 조치를 남긴다.
5. 새 버전 링크를 쓰면 README에서 이동한 운영 한계는 operations의 고정 링크로 연결한다.
6. 이번 정적 확인을 실행·운영 효과 검증으로 보고하지 않는다.

이 보고서는 원고 수정 완료나 독립 검증자의 편집 승인으로 사용하지 않는다.
