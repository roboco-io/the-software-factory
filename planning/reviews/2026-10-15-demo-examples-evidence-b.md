## 판본 비교

후보는 이전 커밋보다 3커밋 앞선다. 직접 비교한 핵심 코드 15개는 이전·후보 blob SHA가 모두 같다. 따라서 단지 최신 후보가 있다는 이유로 기존 코드 인용 URL의 버전을 바꿀 필요는 없다. 이번 작업의 주된 수정은 독자 해설의 배치이며 구현 원리의 정정은 아니다.

README는 대폭 줄었고 설치·운영·실험·보안 한계는 새 `docs/operations.md`로 분리되었다. 현재 독자 안내가 보안 한계를 README만 가리키면 찾기 어렵다. 해당 항목에는 두 문서의 역할을 구분해 연결한다. 후보의 README는 책과 데모의 관계, 서비스·대시보드 주소, 처리 개요, 자기 개선 PoC를 소개한다. 실제 운영 성과는 입증하지 않는다.

## B01 — 전체 예제의 소개와 근거 등급

- 위치: 1장 ‘구현 예제에서 판단의 연결을 읽는다’, S59.
- 문제/영향: 예제 저장소를 여는 독자가 코드부터 볼 수 있다. 무엇을 관찰할지 먼저 안내할 필요가 있다.
- 최소 수정: 본문의 서비스·요청·구현·검토·배포 개요와 직접 실행하지 않았다는 한계를 유지한다. 다단계 구조는 독자용 `/demo/` 개요로 연결한다. 배포 사이트는 체험 링크로 유지한다.
- 수용 조건: 저장소·배포 링크를 열지 않아도 공통 예제의 목적과 관찰 범위를 이해한다. 책의 세 축을 모두 완성한 일반화된 운영 검증으로 쓰지 않는다.

## B09 — 만드는 권한과 게시하는 권한

- 위치: 9장 ‘결과를 만드는 단계와 게시하는 단계를 나눈다’, S64·S59.
- 확인: `factory-implement.yml`의 prepare/agent/publish 정의, 계획 artifact ID 고정 전달과 게시 토큰 배치, `implement.ts`의 계획·번들 생성/게시, `protect.ts`의 head·조상 관계·변경 경로 재확인.
- 현재 문단은 대체로 정확하지만 설명 밀도가 높고 링크명이 ‘구현 워크플로’여서 읽을 이유가 불명확하다.
- 최소 수정: 본문은 ‘에이전트는 변경을 만들고, 별도 게시 단계가 계획과 전달 결과를 확인해 저장소에 올린다. 게시용 App 토큰은 수행 단계에 직접 넘기지 않는다’ 수준으로 압축한다. 여러 파일이 연결되는 상세는 독자 해설로 이동한다.
- 독자 해설 읽는 순서: workflow(실행 환경/토큰 배치) → implement(계획/결과의 전달) → protect(게시 직전 검증) → operations(남은 runner·캐시 위험).
- 한계: agent job에 App 토큰이 없다는 설정과 GitHub 런타임을 포함한 모든 자격 증명이 없다는 주장은 다르다. operations는 runner·캐시 오염 위험을 명시한다. 완전 격리, 실제 App 권한, 사업적 결과 수용까지 입증하지 않는다.
- 수용 조건: 본문에서 토큰 분리와 완전 격리를 혼동하지 않고 독자 해설의 각 링크에 확인 대상을 붙인다.

## B11 — 역할을 배정하고 실제 호출로 연결하기

- 위치: 11장 ‘역할별 실행 조합’ 사례, S65.
- 확인: `factory/agents.yml`이 역할별 엔진과 예산을 선언하고 `config/agents.ts`가 이를 읽어 배정한다. 구현 엔진은 라벨 또는 기본값으로 정하고 검토는 다른 엔진을 선택한다. 선택 불가 시 오류가 난다.
- 호출부 대조: implement 준비가 배정·모델·예산을 계획으로 넘기며 실제 adapter를 호출한다. review 준비는 PR 메타의 구현 엔진을 기준으로 다른 검토 엔진을 배정하고 실패하면 사람에게 넘긴다. review 실행은 readOnly와 검토 예산을 전달한다.
- 최소 수정: 본문에는 선언·배정·호출이 연결됨을 짧게 설명하고 설정 파일 하나가 독립 검증을 보장하는 듯한 해석을 피한다. 관계는 독자 해설로 연결한다.
- 수용 조건: 다른 엔진이라는 형식 조건과 서로 다른 오류를 실제 발견하는 능력을 구분한다. 구체 모델/가격 기본값을 추천으로 옮기지 않는다.

## B17 — 지표의 창과 분모를 함께 읽기

- 위치: 17장 주간 지표 사례, S66.
- 확인: `weekly.ts`는 현재 시점에서 7일 이전 이후의 기록을 골라 `completionRate` 등에 넘긴다. `metrics.ts`는 그 창 안에 구현 기록이 있는 이슈를 분모로 삼고 배포 성공이 있으면서 해당 창의 모든 기록이 성공인 이슈를 완주로 센다. 정책 보류도 완주율에서는 제외되지만 실패 유형 순위/개선 후보에서는 별도로 제외된다.
- 비용은 알려진 값만 합산하고 알려진 기록 수를 함께 남긴다. 표본 5미만이면 비율을 데이터 부족으로 표시한다. `runs/store.ts`는 기록 스키마와 월별 저장 경로를 보여 준다.
- 최소 수정: 본문의 정확한 분모 설명은 유지하되 단독 ‘주간 지표 코드’를 독자용 지표 해설로 바꾼다. 수집→창 제한→계산→해석을 함께 설명한다.
- 한계: 관측 창 경계에서 진행중인 요청/재시도가 나뉠 수 있다. 인간 이관은 실패의 원인과 구분해야 한다. 인과 생산성·총비용·대시보드의 모든 계산이 증명되는 것은 아니다.
- 수용 조건: ‘완주율’이 사용자 결과나 생산성과 동의어가 아니며 분모/창/보류/누락을 독자 스스로 판별할 수 있다.

## B19 — 규칙을 추가한 일과 실패를 잡게 된 일

- 위치: 19장 개선 평가와 PR47/48 사례, S67·S68·S59.
- 확인: collect는 정책 보류와 improve 자체 실패를 개선 후보 집계에서 제외한다. 같은 범주에 distinctKey가 3개 이상이면 후보가 될 수 있다. 일반 실행·검토는 이슈, smoke는 날짜, revert는 커밋이 distinctKey이므로 모든 후보가 ‘서로 다른 이슈 3건’인 것은 아니다.
- improve는 허용 파일을 제한하고 새 평가 사례와 로컬 검사를 요구한다. 게시 때 번들에서 변경 파일을 다시 검증한다. eval은 봇 개선 PR에 새 사례를 요구하며 새 사례의 base 미검출/head 검출과 기존 사례 회귀/수정/삭제를 검사한다. 사람이 만든 PR에는 일부 조건이 다르다.
- 코드·워크플로·문서가 연결되므로 독자용 ‘실패를 규칙으로 바꾸는 과정’ 해설에 모은다. 책의 비타협 원칙·정책 계층 전체가 이 데모에 이미 구현됐다고 쓰지 않는다. 허용 경로 안에도 AGENTS.md가 있으므로 계층 보호를 별도 구현 사실로 보아서는 안 된다.

### 과거 실행 사례 유지 권고

**PR47/48은 삭제하거나 최신 후보 실행으로 바꾸지 말고 2026-10-12 리허설로 유지한다.** 이번 확인에서 PR47은 병합, PR48은 draft·미병합 종료였다. PR47의 원 job은 새 error-format 사례를 이전 규칙은 놓치고 변경 규칙은 잡았다고 기록한다. PR48의 원 job은 같은 직접 오류 반환을 lint가 검출해 종료 코드1로 끝났음을 보여 준다.

이 기록은 후보 버전의 새 실행이 아니다. PR47 base/head와 PR48 tested merge는 동명 JSON에 구분했다. 잘못된 지시를 의도적으로 주입한 실험이라는 설명은 후보 README/operations에서도 확인했다. 자연 발생 실패 감소·장기 개선·정책 계층 준수의 증거로 확대하면 안 된다. job 로그가 향후 보존기간 때문에 사라지면 PR 본문과 당초 확인 기록의 범위를 표시하고 로그 재확인 완료로 보고하지 않는다.

- 수용 조건: 본문에는 날짜·의도적 리허설·검출 변화만 짧게 남긴다. 원 로그 링크는 독자 해설에서 ‘무슨 판정을 볼 수 있는지’를 설명한다. S68은 기존 역사 판본을 보존한다.

## 처리 권고와 미확인

의미가 달라진 핵심 코드 없음. README의 상세 안내 이동은 출처 보조 링크에 반영할 필요가 있다. 파일 관계가 핵심인 9·11·17·19장 사례는 해설 페이지가 적합하다. 1장은 그 페이지의 개요/찾아가기 역할을 맡는다. 모든 권고는 원고 수정 전 상태이며 별도 수정 검증자가 변경본에서 닫아야 한다.
