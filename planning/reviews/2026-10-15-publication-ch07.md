## 3. 의견

### U001 / P2 / 열림: "자료 확인 범위" 링크가 문장이 약속한 내용을 담고 있지 않다

- 위치 / 버전: 공개본 `/book/ch07/` "출처와 검토" 절 첫 문단(원고 `manuscript/chapters/ch07.md` 96행), 변환 규칙 `website/scripts/publication.mjs` 7·15행. 기준 버전 `2f19b89`.
- 문제 / 독자 영향: 공개 문장은 "주장의 성격과 검토 항목은 "자료 확인 범위"(링크 목적지 `/sources/#refs-ch07`)에 기록한다"이다. 변환 스크립트가 내부 파일인 주장 메모(`research/claims/ch07.json`)로 가는 링크를 공개하지 않기 위해 링크 텍스트를 "자료 확인 범위"로 바꾸고 목적지를 참고문헌의 장별 목록으로 돌린다. 그런데 `/sources/#refs-ch07`에는 출처 ID 여섯 개의 목록만 있고 주장의 성격이나 검토 항목은 없다. 독자는 링크를 따라가도 문장이 말한 정보를 찾지 못하고, 그 정보가 공개되지 않는다는 사실도 알 수 없다.
- 근거 / 확인 수준: 정책 기준 1(내부 링크의 공개 경로 변환)에 해당한다. 원고, 생성 Markdown, 빌드 HTML, 변환 스크립트의 해당 행을 확인했다. 같은 구조의 문장("주장 유형은 [주장 메모]에 기록한다" 등)이 20개 장 모두에 있으나 7장 외의 공개본은 열어 보지 않았다.
- 최소 수정: 변환 규칙에서 주장 메모 링크를 포함한 문장의 서술을 공개 목적지와 맞게 바꾼다. 예를 들어 공개본에서는 "장별 출처 목록은 "이 장의 참고문헌"(링크 목적지 `/sources/#refs-ch07`)에 있다"로 바꾸거나, 주장 메모 링크 구절을 공개본에서 제거한다. 원고 문장을 고치는 방법도 있으나 원고 독자(저장소 독자)에게는 현재 문장이 맞으므로 변환 규칙 수정이 더 작다.
- 수용 조건: 빌드 후 `/book/ch07/`의 "출처와 검토" 문장이 링크 목적지의 실제 내용과 맞는지 읽어 확인한다. 20개 장에 같은 변환이 적용되는지 `dist/book/*/index.html`에서 검색한다.

### U002 / P2 / 열림: 모바일 폭에서 표의 셋째 열이 단서 없이 잘린다

- 위치 / 버전: 공개본 `/book/ch07/` "완료 조건마다 증거와 책임을 연결한다" 절의 표, 스타일 `website/src/styles/book.css` 16행. 기준 버전 `2f19b89`.
- 문제 / 독자 영향: 표는 `display:block; overflow-x:auto`로 가로 스크롤된다. Pixel 5 폭(Chromium)에서 표의 `scrollWidth`는 392px, 보이는 폭은 361px이다. 스크린샷에서 셋째 열 머리글 "리더가 정할 사항"이 "리더가 정할 사"까지만 보이고, 스크롤할 수 있다는 시각 단서가 없다. 이 열은 이 책의 독자인 리더가 결정할 사항을 담은 핵심 열이므로, 독자가 스크롤 가능성을 알아차리지 못하면 표의 결론을 놓친다. 페이지 전체의 가로 넘침은 없으므로 e2e 검사(`document.documentElement.scrollWidth`)는 이 문제를 잡지 않는다.
- 근거 / 확인 수준: 정책 기준 7("모바일 폭에서 표가 가로로 넘쳐 내용이 가려지지 않는지")에 해당한다. 내용은 스크롤로 접근할 수 있으므로 "읽을 수 없게 만드는 문제"(P1)가 아니라 "불편"(P2)으로 판정했다. Chromium 측정과 스크린샷 한 장만 확인했고, iOS Safari와 키보드 스크롤 가능 여부는 확인하지 않았다.
- 최소 수정: 넘치는 표에 스크롤 단서(오른쪽 가장자리 그림자 또는 "옆으로 밀어 보기" 안내)를 추가하고, 스크롤 컨테이너에 `tabindex="0"`과 접근 가능한 이름을 준다. 또는 좁은 폭에서 `td`의 `min-width:8rem`을 줄여 세 열이 361px 안에 들어가게 한다.
- 수용 조건: 모바일 폭에서 7장 표의 셋째 열 머리글이 완전히 보이거나 스크롤 단서가 보인다. e2e에 본문 표의 `scrollWidth > clientWidth`일 때 단서가 있는지 확인하는 검사를 추가하면 다른 장에도 적용된다.

남은 P0·P1은 없다. P2 세 건(U001-U003)이 열려 있다. U001과 U002는 7장 외의 장에도 같은 원인으로 나타날 가능성이 높으므로, 수정은 변환 규칙과 스타일 한 곳에서 하고 책 전체 빌드로 확인하는 편이 작다.

## 6. 정책 시범 메모

다음은 이 리뷰에서 정책을 적용하며 모호했거나, 불필요했거나, 빠졌다고 판단한 점이다. 정책 변경 제안이며 확정된 결정이 아니다.

1. **`STATUS.md` 기록 의무가 서로 충돌한다.** [README](../review-policies/README.md)의 "보고서와 기록"은 리뷰를 마치면 `STATUS.md`에 결과를 남기라고 하지만, `.claude/agents/review-publication.md`의 "쓰기 권한의 한계"는 `STATUS.md` 수정을 금지한다. 네 에이전트가 병렬로 실행될 때 `STATUS.md`를 동시에 고치면 충돌하므로 에이전트 정의가 맞다고 본다. README를 "리뷰를 호출한 쪽(또는 통합 단계)이 네 보고서를 모은 뒤 `STATUS.md`에 기록한다"로 바꾸기를 제안한다.

2. **체인지 로그의 "부분 기록"에 대한 등급 기준이 없다.** 기준 4는 중요한 변경이 "기록되지 않았으면 P1"이라고만 한다. U003처럼 변화가 일반 문장에는 들어 있지만 해당 장을 가리키지 않는 경우를 P1로 볼지 P2로 볼지 정할 근거가 없어 P2로 판단했다. "독자가 해당 장을 찾을 수 없으면 P2, 변화 자체가 없으면 P1"처럼 기준을 나누기를 제안한다. 또한 revision을 올린 장마다 체인지 로그 링크가 있어야 하는지(revision과 로그의 대응 규칙)도 정해 두면 판정이 기계적으로 쉬워진다.

3. **"직전 공개 커밋"을 찾는 방법이 없다.** 정책은 "기준 버전과 직전 공개 커밋 사이의 `git diff --stat`"을 요구하지만, 공개 커밋이 푸시된 커밋(`origin/main`)인지, 배포 워크플로가 성공한 커밋인지, 사이트에서 확인한 커밋인지 정의하지 않는다. 이번에는 `origin/main`(`121e501`)을 쓰고 배포 사이트의 `data-reader-revision`으로 보조 확인했다. 배포 성공 커밋을 확인하는 명령(예: `gh run list --workflow pages.yml --branch main --status success -L 1 --json headSha`)을 정책에 넣기를 제안한다.

4. **변환된 링크 문장의 진실성을 확인하는 기준이 없다.** 기준 1은 내부 링크가 공개 경로로 "변환되는지"만 묻는다. U001은 변환이 성공했지만 문장이 목적지와 맞지 않는 경우다. `publication.mjs`가 링크 텍스트를 바꾸는 규칙(주장 메모, 연구 대응 지도)마다 "변환 뒤 문장이 목적지 내용과 맞는가"를 표본 확인하는 항목을 기준 1에 추가하기를 제안한다.

5. **모바일 표의 판정 기준이 측정 가능하지 않다.** 기준 7의 "표가 가로로 넘쳐 내용이 가려지지 않는지"는 스크롤 가능한 표를 통과로 볼지 실패로 볼지 정하지 않는다. 현재 e2e는 페이지 전체의 가로 넘침만 검사하므로 표 내부의 잘림을 잡지 못한다. "표 내부가 넘치면 스크롤 단서와 키보드 접근이 있어야 한다"처럼 기준을 정하고 e2e 검사로 옮기기를 제안한다.

6. **앵커 기준이 manifest 앵커만 다룬다.** 공개본에는 manifest의 고정 앵커(`s01` 등)와 Starlight가 절 제목에서 만드는 앵커(`#완료-조건마다-증거와-책임을-연결한다`)가 함께 있고, 페이지 목차와 독자가 복사하는 링크는 후자를 쓴다. 절 제목을 바꾸면 후자는 깨진다. 기준 3에 "절 제목 변경 시 제목 앵커로 들어오는 외부 링크가 끊긴다는 점을 체인지 로그나 리다이렉트로 처리했는가"를 넣을지 저자의 판단이 필요하다.

7. **장 범위 리뷰에서 책 전체 기준의 적용 범위가 모호하다.** 기준 5(라이선스)와 6(메타데이터)은 대부분 책 전체에 걸린 사항이다. 장 범위 리뷰에서 이를 매번 전부 확인하면 같은 확인이 장마다 반복되고, 일부만 확인하면 범위가 불분명해진다. 이번에는 7장 페이지에 나타나는 표시(머리 상태, 바닥글 라이선스, 메타 설명)와 7장 메타데이터 행만 확인했다. "장 범위에서는 해당 장 페이지에 나타나는 표시와 그 장의 메타데이터 행만 확인하고, 책 전체 항목은 책 범위 리뷰에서 한 번 확인한다"고 명시하기를 제안한다.

8. **병렬 리뷰에서 빌드가 같은 산출물을 덮어쓴다.** 네 에이전트가 같은 작업 트리에서 `npm run build`나 `npm run content`를 실행하면 `dist/`와 `src/content/docs/`를 동시에 다시 쓴다. 이 축만 빌드를 실행하거나, 출판 축이 별도 작업 트리(git worktree)에서 빌드하도록 정하기를 제안한다.

9. **`git diff --check`는 깨끗한 기준 버전에서는 확인하는 것이 없다.** 정책이 커밋된 기준 버전을 요구하므로 작업 트리 기준의 `git diff --check`는 항상 통과한다. 의미 있는 검사는 `git diff --check <직전 공개 커밋> <기준 버전>`이다. 명령을 이렇게 바꾸기를 제안한다.

10. **배포 사이트 확인이 선택 사항이라 "공개 예정" 판정의 근거가 약하다.** 기준 4는 공개된 항목과 공개 예정 항목의 구분을 보라고 하지만, 실제 공개 여부를 확인하는 절차를 요구하지 않는다. 이번에는 배포 사이트의 revision을 조회해 공개 예정이 맞음을 확인했다. 기준 4에 "공개 예정 항목은 배포 사이트에서 미반영을, 날짜 항목은 반영을 확인한다(URL과 시각 기록)"를 넣기를 제안한다.

11. **보고서 자체가 구조 검사의 대상이 된다.** `scripts/check_project.py`는 `planning/reviews/`의 보고서도 로컬 링크 검사 대상에 넣고, 코드 표기(백틱) 안의 링크 문법도 검사한다. 공개 경로(`/sources/...`)를 마크다운 링크 형태로 인용하면 검사가 실패하므로, 이번 보고서는 공개 경로를 링크가 아닌 문장으로 적었다. 정책의 보고서 형식에 "공개 사이트 경로는 링크 문법으로 쓰지 않는다"를 넣거나, 검사가 코드 표기를 건너뛰도록 고치기를 제안한다.

조정자의 요청으로 다른 축이 넘긴 네 사항을 같은 기준 버전(`2f19b89`)과 같은 정책으로 판정했다. 판정 시점(2026-10-15 09:04 KST)에 추적 파일의 변경은 없었다. `website/dist/`는 다른 에이전트가 09:04:04에 다시 빌드한 산출물이었고, 다시 빌드하지 않고 이 산출물을 사용했다. 이 산출물의 `dist/book/ch07/index.html` SHA-256(`bf0370779bc1ab2d…`)은 앞서 이 리뷰에서 직접 빌드한 결과와 같다. 네 사항 모두 새 의견을 만들지 않았다.
