# 전체 원고의 다이어그램·예시 보강 제안

## 범위와 판본

2026년 10월 24일, 서문·20장·15개 패턴·9개 데모 해설의 **독자용 원고 45개를 모두 읽었다**. 내부 조사·출처 원문 전체를 다시 읽은 검토는 아니다. 패턴 카탈로그와 웹 패턴 사전의 구성도 확인했다. 검토 기준은 집필 지침, 논증·구조 및 독자·문체 리뷰 정책이다. 독자 이해를 돕는 편집 제안이며, 전체 사실 검증·독립 리뷰·실제 독자 시험은 수행하지 않았다.

기준 HEAD는 `778d60080c5f3834fed825d19a5adddac01d4ae2`다. 미커밋 서문을 포함한 실제 검토 파일의 SHA-256과 완독 목록은 [판본·읽기 목록](2026-10-24-diagram-example-inventory.json), 장별 상세 관찰은 [읽기 메모](2026-10-24-diagram-example-reading-notes.md)에 남겼다. 앞선 집필 도구 공개와 공유 메타데이터 변경은 보존했다.

현재 원고에는 마크다운 표 43개와 다이어그램 SVG 2개가 있다. 3장의 정책 계층, 9장의 의도 중심 하네스 사이클은 이미 중요한 관계를 설명한다. SVG의 소스·문구·연결 구조를 확인했으며 이번에 화면 배치를 다시 시험하지는 않았다. 문의 초안·연락처 변경·발송 결과 미확인 등 기존 예시도 여러 장에 있다.

따라서 **장마다 그림을 넣기보다, 관계·분기·시간을 그림으로 보완하고 같은 업무의 판단 예시를 이어 쓰는 방식**을 권한다. 새 로봇 삽화나 장식 그림은 삽화 보류 결정을 유지한다. 아래 항목은 모두 저자 검토를 위한 제안이며 원고에는 적용하지 않았다.

## 다이어그램 상세안

### R01 / P2 / 제안 — 1장의 전체 지도

**위치:** [1장](../../manuscript/chapters/ch01.md) 「모델·에이전트·하네스가 함께 일한다」 뒤.

**문제와 독자 영향:** 목표·세 원리·실행 구성요소·보안이 각각 설명되지만, 처음 읽는 리더는 이들의 포함 관계와 결과가 돌아오는 경로를 머릿속에서 조립해야 한다. 현재 두 표는 관계 전체를 보여 주지 않는다.

**최소 보강:** 상단에 고객 문제·기대 사업 성과·보안/신뢰성/비용 조건을 두고, 의도 정의와 개선 → 정책에 따른 계획·수행 → 증거와 운영 결과의 흐름을 그린다. 실제 결과에서 의도와 하네스 양쪽으로 환류한다. 에이전트는 모델·도구를 사용하며 하네스 사이클 안에서 일하는 관계로 표현한다. 보안은 설계부터 운영·종료까지 이어지는 공통 조건으로 표시한다.

**표현 제한:** 세 제품 구매 목록이나 코드 생산 공정으로 그리지 않는다. 모델·에이전트·하네스를 서로 독립된 상자로만 나열하지 않는다. 운영 결과 확인을 배포 성공으로 끝내지 않는다. 사람이 모든 실행의 통과문에 서는 그림도 피한다.

**수용 조건:** 그림만 보고도 목적, 세 원리의 역할, 모델과 에이전트의 관계, 운영 증거의 환류를 설명할 수 있어야 한다. 서문에서는 이 그림을 참조하고 상세 지도를 반복하지 않는다. 근거는 현재 1장과 집필 정의의 대조이며 새 외부 사실은 없다.

### R02 / P2 / 제안 — 4장의 두 개선 루프

**위치:** [4장](../../manuscript/chapters/ch04.md) 「의도의 개선과 하네스의 개선을 연결한다」 뒤.

**문제와 독자 영향:** 현재 산문은 두 개선을 구분하지만, 같은 실패에서 어느 대상을 고칠지 한눈에 대조하기 어렵다.

**최소 보강:** 공통 운영 증거에서 두 경로로 나눈다. 의도 루프는 고객 문제·기대 결과·성공 기준의 재검토로, 하네스 루프는 맥락 공급·지침·계획·도구 집행·검증의 개선으로 이어진다. 각 변경은 권한 확인과 평가를 거쳐 다음 실행에 적용한다. 개별 작업의 재시도는 별도의 작은 경로로 구분한다.

**표현 제한:** 운영 결과가 나쁘다고 목표나 정책을 자동으로 낮추지 않는다. 의도 변경과 하네스 변경의 권한이 같다고 가정하지 않는다. 최상위 원칙은 두 개선에서 보존한다.

**수용 조건:** ‘잘못된 목표를 정확히 수행한 경우’와 ‘적절한 목표를 잘못 수행한 경우’가 서로 다른 변경 대상으로 연결되어야 한다. 9장의 기존 사이클은 집행·책임을 확대 설명하는 그림으로 남기고, 19장은 이 그림을 참조한다.

### R03 / P2 / 제안 — 3장의 실행 경로 분기

**위치:** [3장](../../manuscript/chapters/ch03.md) 「완전 자동화할 범위를 원칙과 정책으로 나눈다」 뒤.

**최소 보강:** 요청·맥락 → 적용 원칙과 정책 확인 → 허용 범위·필요 증거·실제 권한·복구 조건 확인 → 경로 분류를 그린다. 출력은 ‘허용된 자동 처리’, ‘정책이 유보한 사람 판단’, ‘조건 미확인·충돌에 따른 보류’, ‘원칙상 금지에 따른 차단’이다. 보류에서는 허용된 추가 조사만 수행하고 다시 분류할 수 있다. 사람 판단에서도 원칙상 금지를 임의로 해제할 수 없다.

**독자 영향과 중복 억제:** 정책 계층 그림과 자연언어/YAML 예시는 이미 있으므로 다시 만들지 않는다. 새 그림은 정책의 표현 형식이 아니라 실제 실행 경로를 설명한다.

**수용 조건:** 조건이 충족된 범위는 개별 승인 없이 끝나야 한다. 단방향 결정·높은 위험이라는 이유만으로 사람 판단에 고정하지 않는다. 반대로 데이터 노출처럼 회수가 불가능한 영향은 원칙과 권한 조건에서 엄격히 평가한다. 권한 변경은 구조화된 조건으로 사람 확인 대상 여부를 판별하고, 비용 절충은 위임 범위를 넘는 판단을 사람에게 이관하는 기존 예시와 맞춘다.

### R04 / P2 / 제안 — 9장의 책임과 수행 흐름

**위치:** [9장](../../manuscript/chapters/ch09.md) 「작은 팀에서는 책임을 겸임하고 판정 경로를 분리한다」 뒤.

**최소 보강:** 하나의 업무를 제품 결과 책임, 정책·위임 경계, 하네스 운영, 자동 수행·판정의 논리적 책임별 행으로 나눈다. 목표와 위임 조건을 정하는 시점, 정책 안에서 반복 실행하는 시점, 예외와 운영 결과로 기준을 고치는 시점을 구분한다. 같은 사람이 여러 책임을 맡을 수 있음을 겸임 표시로 보여 준다.

**독자 영향:** 기존 책임표의 정적 배치를 실제 작업의 흐름으로 읽게 한다. 공유 조직이 없는 소수 인원 기본형에서 출발한다. 기존 의도 중심 사이클은 유지한다.

**수용 조건:** 행 수가 필수 인원 수를 뜻하지 않아야 한다. 책임 겸임이 판정 경로의 독립성을 자동 보장하지 않으며, 자동 판정과 결과 책임이 함께 존재함을 캡션으로 설명한다. 13·15·16장은 필요한 부분만 참조한다.

### R05 / P2 / 제안 — 18장의 두 도입 여정

**위치:** [18장](../../manuscript/chapters/ch18.md) 「신규 서비스는 목표와 운영 경계를 함께 구축한다」 뒤.

**최소 보강:** 기존 서비스 경로에는 고객 약속·데이터·현재 성능·회귀와 이관 조건을, 신규 경로에는 사업 가설·작은 사용자 흐름·초기 실행 기반을 둔다. 두 경로를 제한된 시험 → 증거 관찰 → 유지/보완/중단/확대로 연결한다. 20장의 확대·종료 판단까지 연결한다.

**표현 제한:** 신규 서비스에 기존 운영 기준선이 있다고 그리지 않는다. 초기 기반을 구축하는 신뢰할 수 있는 실행자의 권한과 제품 에이전트의 실행 권한을 구분한다. 전면 재작성이나 기술 스택 교체를 필수 단계로 넣지 않는다.

**수용 조건:** 두 경로의 준비 조건과 공통 평가 기준이 드러나야 한다. 한 장의 복잡한 그림보다 두 경로의 작은 패널과 공통 판정 패널을 사용한다. 기존 비교표는 차이를 찾는 용도로 유지하되 같은 설명 문구를 중복하지 않는다.

### R06 / P2 / 제안 — 17장의 지표 포함·제외 관계

**위치:** [17장](../../manuscript/chapters/ch17.md) 「결과와 분모를 먼저 정한다」 뒤. 데모 지표 해설에서 구체적 계산 범위를 연결한다.

**최소 보강:** 전체 요청 집합, 정책에 따라 자동 처리할 수 있는 집합, 실제 실행·자동 완주한 집합을 구분한다. 사람 판단과 보류를 전체 요청에서 지우지 않는다. 관찰 기간을 걸치는 요청과 미보고 비용도 별도 표시한다. 집합의 넓이는 비율을 뜻하지 않는다고 밝힌다.

**수용 조건:** 자동화 가능 범위 대비 완주와 전체 요청 대비 자동 완주가 다른 질문임을 읽을 수 있어야 한다. 어떤 집합을 분모로 골랐는지 명시한다. 가상 성과 수치를 넣지 않는다. 데모가 실제 사용하는 분모와 책이 제안하는 분모를 같은 것으로 표시하지 않는다.

### R07 / P2 / 제안 — 데모 전체 흐름과 권한 경계

**위치:** [데모 목록](../../manuscript/demo/index.md) 「먼저 볼 흐름」 뒤, 상세 확대는 [만드는 권한과 게시하는 권한](../../manuscript/demo/execution-authority.md) 「계획과 결과가 권한 경계를 건넌다」 뒤.

**최소 보강:** 전체 그림은 요청·시작 허용 → 준비·수행 → 검사·검토·병합 → 배포 → 실행 기록과 개선 후보를 해설 페이지로 연결한다. 실제 확인 버전에서 사람의 시작 판단이 있고, 일부 병합·개선 반영이 사람 판단으로 간다는 점을 표시한다. 상세 그림은 준비/수행/게시 환경, 계획·변경 묶음의 전달, 각 단계의 자격 증명, 게시 직전 신뢰하는 기준 코드의 확인을 보여 준다.

**수용 조건:** 책의 목표와 확인한 데모의 현재 선택이 구분되어야 한다. 준비 단계도 App 토큰을 쓴다는 사실을 빠뜨리지 않는다. 수행 단계에 게시 토큰을 주지 않는 것을 완전한 격리로 표현하지 않는다. 버전·확인 범위를 해설과 공유하고, 구현에 없는 자동화·우회 불가능성은 그리지 않는다. 그림 제작 때 데모 유지관리 정책에 따라 근거를 재대조해야 한다. 이번 작업은 데모의 최신 버전 재조사가 아니다.

### R08 / P3 / 제안 — 6·8·14장의 선택 도표

세 개 모두 유용하지만 첫 묶음에는 넣지 않아도 된다.

| 위치 | 최소 그림 | 수용 조건 |
|---|---|---|
| 6장 「의존성과 병렬 실행의 조건을 드러낸다」 | 문의 처리의 결과 의존성: 근거 탐색과 수신 대상 사전 확인 → 초안·통합 → 최종 조건 재확인 | 모든 단계의 병렬화를 암시하지 않는다. 사전 권한 확인이 발송 시점까지 유효하다고 가정하지 않는다. |
| 8장 「같은 요청을 다시 해도 되는지 확인한다」 | 발송 후 응답 누락 → 결과 조사 → 전달 확인/안전한 재시도/보류 | 응답 누락을 발송 실패로 처리하지 않는다. 조사 자체도 권한 안에서 수행한다. |

### R09 / P2 / 제안 — 문의 업무의 판단 카드 묶음

**문제:** 현재 여러 장의 예시가 원칙을 설명하지만, 한 업무의 의도·계약·판정·복구를 독자가 완성된 형태로 대조하기는 어렵다. 각 장에 새 서비스를 등장시키면 추가 맥락을 배워야 한다.

**최소 보강:** 기존 문의 업무를 공통 설명 예시로 삼는다. 아래 문구는 제작 방향을 보여 주는 설명용 초안이며, 실제 고객 사례나 데모의 구현 사실을 뜻하지 않는다. 정책 조건은 해당 예시에 적용하는 조건으로 명시한다. 임의의 수치·가짜 운영 성과는 넣지 않는다.

| 장·위치 | 추가할 짧은 예시 | 독자가 확인할 판단 |
|---|---|---|
| 2장 「목적과 요청한 방법이 같은지 확인한다」 | ‘문의 챗봇을 만든다’에서 ‘문의자가 현재 적용되는 근거와 필요한 다음 행동을 찾도록 한다’로 의도 구체화. 보호 조건과 실제 사용 확인을 붙임 | 방법의 완성과 고객 문제의 해결이 다름 |

| 19장 「증상과 확인한 원인, 남은 가설을 나눈다」 | 오래된 안내를 사용한 동일 증상에서 자료 갱신 누락/모호한 지침/명확한 지침의 집행 실패를 대조 | 각각 자료·정책·집행을 다르게 고치며 평가함 |

**수용 조건:** 계약의 위임 범위가 장 사이에서 일치해야 한다. 범위가 달라질 때 변경 사실과 새 조건을 밝힌다. 그림·본문·캡션에서 설명 예시와 확인한 데모 사실을 분리한다. 기존 유사 문단을 이 예시로 정리해 총분량 증가를 줄인다.

## 패턴과 데모의 보강 범위

패턴 15개마다 그림을 만드는 것은 권하지 않는다. 현재 사전은 목적과 연결 장을 제공하므로 이를 유지한다. P03 ‘실행 가능한 계약’에는 계약 카드, P06 ‘증거 기반 완료’에는 증거 카드, P10 ‘범위가 정해진 자율성’에는 분기 그림, P11 ‘예외를 통한 개입’에는 복구 사례, P14 ‘흐름에 맞춘 권한과 팀 경계’에는 책임 흐름, P15 ‘검증을 거치는 개선’에는 두 루프를 연결한다. 각 패턴은 필요하면 적용/비적용 상황 한 쌍만 덧붙인다. 관계가 많은 15노드 전체 연결망보다 이 방식이 현재 질문별 독서에 맞는다.

| 데모 해설 | 제안 |
|---|---|
| 목록 | 전체 흐름과 각 해설로의 연결 그림 |
| 요청 | 전체 그림을 참조하고, 정리와 시작 허용의 차이를 짧게 유지 |

| 증거 | 수정 전 실제 검사 실패/환경 오류/수정 후 통과를 비교한 상태표 후보 |
| 복구 | 새 작업 차단·개별 취소·외부 효과 복구의 세 범위를 작은 표로 대조 |

## 제작·검증 기준

1. 구조·분기·관계는 기존 SVG와 같은 편집 가능한 벡터 방식으로 만든다. 별도 화풍의 장식 삽화는 생성하지 않는다. 기존 그림과 글꼴·선·색의 의미를 맞춘다.
2. 그림마다 독자가 답할 질문 하나를 정한다. 화살표가 순서·정보 전달·통제·환류 중 무엇인지 표시한다. 복잡하면 확대도나 두 패널로 나눈다.
3. 그림 밖의 짧은 캡션으로 핵심 판단과 적용 한계를 설명한다. 대체 텍스트 또는 인접 설명만으로도 같은 뜻을 이해할 수 있게 한다. 색만으로 자동·사람·보류를 구분하지 않는다.
4. 모바일에서 전체 축소만 하지 않는다. 작은 글씨가 필요한 그림은 세로 배치·분할을 우선하고, 데스크톱과 모바일에서 문구·화살표·스크롤을 확인한다.
5. 본문 기존 예시와 표를 먼저 통합한다. 그림을 추가한 뒤 같은 관계를 다시 길게 설명하는 문단은 줄이되 권한·증거·확인 한계는 보존한다.
6. 새 합성 예시는 설명용임을 밝히고 실제 사건·수치·효과를 만들지 않는다. 데모 그림은 고정 판본의 확인 사실과 책의 제안을 구분하고 유지관리 정책에 따라 갱신한다.
7. 적용 후 장 사이의 계약·권한 일관성, 출처·패턴 연결, 안정 앵커와 토론 링크, 빌드·내부 링크·모바일 가독성을 확인한다. 실제 독자 시험을 하지 않았다면 이해 효과를 검증했다고 보고하지 않는다.

## 판정과 인계

전체 독자 원고의 읽기와 보강 후보 정리는 완료했다. R01~R10은 모두 **제안·저자 판단 대기**다. 그림·예시 제작, 본문 편집, 화면 검증, 독자 이해 시험은 수행하지 않았다. 이 검토만으로 기존 원고의 사실·출판 상태를 승격하지 않는다.

첫 실행 묶음은 **1장 전체 지도, 4장 두 루프, 2·5·7·8장의 연결 예시**를 권한다. 이후 3·9·17·18장과 데모 그림을 추가한다. 선택 도표와 각 장의 짧은 예시는 첫 묶음의 분량과 중복을 본 뒤 결정한다. 제안만 작성했으므로 독자용 체인지 로그는 추가하지 않는다.
