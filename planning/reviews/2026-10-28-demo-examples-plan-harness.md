# 데모의 실행계획·하네스 구분 점검

## 범위와 결론

2026-10-28 기본 브랜치의 후보를 `b925518f535b49f3383b23db52cc66e8139ce042`로 고정해 확인했다. 책 기준은 `54eb0e0`의 D57이다. 기존 책 해설의 고정 판본 `5b1927f`와는 41개 커밋 차이가 있다. 변경 파일 목록으로 조사 범위를 골랐으며 전체 변경·제품 앱의 재검토는 아니다. [출처·주장 매니페스트](2026-10-28-demo-examples-plan-harness-manifest.json)에 취득한 30개 파일의 SHA·고정 URL·실제 확인 범위를 남겼다.

**대체로 책의 구분에 맞는 구조다. 전면 재설계보다 계획의 의미와 실행 판본·이력 연결을 보강하는 편이 적절하다.** 하네스는 한 디렉터리나 프로그램이 아니라 워크플로·CLI 실행기·정책·판정·기록·운영 관찰을 합친 체계로 읽을 수 있다. 현재 `ImplementPlan`을 그 전체와 동일시할 근거는 없다.

다만 현재의 `*Plan`은 단계 사이의 실행 요청 데이터라는 의미가 강하다. 업무별로 고른 작업 순서와 의존 관계를 명시하고 변경 이유까지 남기는 실행계획은, 확인한 구현 경로에서 별도 산출물로 드러나지 않는다. 공통 작업 순서는 코드와 프롬프트에 이미 있다. 에이전트가 내부적으로 계획하지 않는다는 뜻이나 모든 작은 작업에 별도 계획서가 필요하다는 뜻은 아니다.

적용 기준은 책의 D57·용어집, 데모 사례 갱신 정책의 점검 모드, development:code-review 스킬이다. 외부 저장소 문서와 주석은 근거 자료로만 읽었다. 데모 실행·테스트 수행·실제 저장소 권한 설정·운영 성과는 확인하지 않았다. 확인한 테스트는 정의를 읽은 것이며 통과를 새로 주장하지 않는다.

## 현재 구현에서 확인한 분리

|---|---|---|

| 이력·개선 | 런 저장·실패 수집·포스트모템·개선 PR과 평가 경로가 있다. | 지침/규칙 개선의 경로는 있으나 모든 하네스 구성요소를 자동 수정하는 체계는 아니다. |

## 개선 우선순위

아래 P1·P2는 개선의 우선순위다. 정적 점검만으로 재현한 취약점이나 실제 장애의 심각도 판정이 아니다. 제안 상태이며 미구현이다.

### DP01 / P1 / 실행 요청서와 작업 계획을 구분

- 위치/근거: 현재 `implement.ts:46–59`와 준비/수행 함수, `review.ts:46–63`, `fix.ts:36–51`. 요청 데이터와 실제 수행 경로를 함께 읽었다.
- 영향: 현재 객체 이름만 보면 책의 실행계획에 단계·의존성·검증 방법까지 이미 표현되어 있다고 오해하기 쉽다.
- 최소 개선: 먼저 문서에서 현재 Plan을 ‘단계 실행 요청서’로 설명한다. 필요하면 타입을 `ImplementRunSpec`처럼 바꾸고 그 안에 업무별 `workPlan`을 연결한다. 즉시 대규모 이름 변경을 할 필요는 없다.
- 저자 제안: 복잡한 작업의 계획에는 작업 ID, 기대 산출물, 의존 관계, 확인할 증거, 허용된 재계획 조건을 둔다. 단순 작업은 한 단계로 충분하다. 공통 워크플로를 매 작업의 계획서에 복제하지 않는다.
- 수용 조건: 같은 실행기에서 서로 다른 작업 계획을 처리할 수 있고, 계획 변경으로 실제 권한·수용 기준이 확대되지 않아야 한다. 정책 안의 재계획에 매번 사람 승인을 붙이지 않는다. 실제로 실행한 단계·변경 이유와 원래 계획도 구분해 남긴다.

### DP02 / P1 / 실행 판본과 증거를 한 번에 추적

- 위치/근거: `factory-implement.yml:39–40,79–80,126–127`는 단계별 runtime을 `main`에서 가져온다. 준비 산출물의 artifact ID와 제품의 `baseSha`를 고정하는 장점은 이미 있다. `RunRecord`는 역할·비용·결과 등의 기록이지만 공통 계획/하네스/정책 판본 필드를 갖고 있지 않다.
- 영향/추론: 긴 실행 도중 main이 바뀌면 단계별 코드·정책이 서로 다른 판본일 가능성이 있다. 이것이 실제 사고를 일으켰다고 확인한 것은 아니다. Actions 기록·PR·아티팩트로 일부 추적이 가능하므로 ‘이력이 전혀 없다’고 하지 않는다.
- 최소 개선: `runId`, `planId/revision`, 제품 `baseSha`, 하네스 `runtimeSha`, 정책·프롬프트 판본/해시, 증거 식별자를 공통 실행 명세와 기록에 연결한다. 고정할 실행 판본과 실행 직전 재확인할 상태를 나눈다.
- 수용 조건: 단계 사이에 main 변경을 넣어 고정한 판본이 유지되거나 명시적인 전환·재검증이 일어나는지 확인한다. **긴급 권한 회수·중단·새 금지 정책까지 과거 스냅샷으로 무효화해서는 안 된다.** 실행 당시 기준과 현재의 철회/차단 판단을 모두 기록한다.
- 참고: 계획 로드는 JSON 파싱과 타입 단언을 쓰므로, 명세가 커질 때 판본별 스키마 검사와 알 수 없는 판본의 보류도 추가한다. 이는 신뢰하는 prepare 아티팩트 경계를 대체하지 않는다.

근거: [단계별 main과 아티팩트 배치](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/.github/workflows/factory-implement.yml), [현재 런 기록](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/packages/factory/src/runs/store.ts#L12-L30). 기록 보관 기간은 필요한 증거·민감정보·비용 조건으로 정한다. 모든 원문을 영구 저장하라는 제안은 아니다.

### DP03 / P1 / 실행 중 통제와 게시 전 거부를 구분

- 위치/근거: `protect.ts`·`worktree.ts`의 변경 재검증과 `claude.ts`의 쓰기 모드, `docs/operations.md`의 팩토리 보안 한계.
- 현재의 장점: 게시 권한 분리와 신뢰하는 준비 아티팩트, 현재 상태·번들·경로의 재확인은 유지할 통제다. 기존 구현 테스트에도 번들의 금지 경로·SHA·기준 커밋 검사가 정의되어 있다.
- 남은 한계: 쓰기 모드는 폭넓은 도구 실행을 허용한다. 운영 문서도 runner·캐시 등의 위험을 수용했다고 밝힌다. 게시 거부로 이미 읽거나 외부로 전달한 정보를 회수할 수는 없다. 이번 점검은 그 위험을 공격으로 재현한 것이 아니다.
- 최소 개선: 운영 범위를 넓히기 전에 데이터 접근·외부 통신·실행 도구·자격 증명을 수행 중 집행할 경계를 별도로 평가한다. 계획이 요청한 접근은 그 자체로 허가가 아니며 독립된 정책과 실행 환경이 제한해야 한다.
- 수용 조건: 금지 경로 변경의 게시 차단 시험과 별도로, 금지된 정보 읽기·외부 전송이 실제 행동 전에 제한되는지 확인한다. runner/캐시 신뢰 경계도 포함한다. 계획과 job을 나눴다는 사실만으로 완전 격리나 정보 보호를 승인하지 않는다.

이 제안은 현재 데모가 명시한 보안 한계를 없앴다고 가정하지 않으며, 책의 구분에 맞는 운영 범위를 판단하기 위한 별도 확인이다. [현재 알려진 한계](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/docs/operations.md#팩토리-보안-한계).

### DP04 / P2 / 정책 판단과 그 집행 경로를 식별

- 위치/근거: `factory/risk-policy.yml`, `policy/risk.ts`, `stages/gate.ts`, `factory/postmortem-policy.yml`.
- 현재 상태: YAML의 경로/검사 선언과 코드에 있는 사람 이관·자동 병합·예외 처리가 함께 정책을 실현한다. 코드로 둔 규칙도 정책을 표현할 수 있으므로 전부 YAML로 옮길 필요는 없다.
- 최소 개선: 자동 처리/사람 판단/보류/차단의 판정 이유와 정책 식별자를 반환하는 경계를 두고, 그 결과를 실제 도구·병합 권한에 연결한다. 자연언어 지침·구조화 규칙·코드·GitHub ruleset 사이의 대응표와 불일치 검사를 둔다. 문서는 이미 ruleset과 필수 체크 목록의 동기화를 수동 책임으로 설명한다. 이번에 실제 설정을 재검증하지 않았다.
- 수용 조건: 기준과 집행의 대응을 정상·금지·누락 입력으로 대조하고, 필수 조건이 불명확하면 통과로 처리하지 않는다. 보호할 기존 조건을 먼저 고정한 뒤 리팩터링한다. T2/T3를 바로 자동 허용으로 바꾸자는 제안은 아니다.

### DP05 / P2 / 실패에서 바꿀 대상을 먼저 분류

- 위치/근거: `postmortem/analysis.ts`의 사고 분류와 사실/가설 구분, `collect.ts`의 실패 후보 수집, `improve.ts`의 개선 종류, `policy/improve-paths.ts`의 허용 범위.
- 현재 상태: 포스트모템과 개선 PR의 연결은 이미 있다. 개선 역할이 다루는 종류는 lint/agents/prompt이며 실제 허용 파일도 제한된다. 사고가 누구의 변경·외부 요인·정체인지 나누는 분류와, 어떤 층을 고칠지 고르는 분류는 다른 축이다.
- 최소 개선: 확인한 원인에 `plan_gap`, `planning_failure`, `policy_gap`, `enforcement_failure`, `implementation_defect`, `unknown` 같은 변경 대상 축을 추가한다. 이름은 설계 제안이며 확정 규격이 아니다. 한 사건이 여러 층에 걸칠 수 있다.
- 수용 조건: 이번 작업의 단계 누락은 계획 보완으로, 반복 누락은 계획 수립 방식으로, 계획에 있던 통제가 작동하지 않은 경우는 집행 장치 변경으로 연결한다. 근거가 부족하면 unknown과 추가 조사를 남긴다. 모든 사건을 프롬프트 추가로 해결하지 않는다.
- 권한: 하네스 런타임·워크플로 변경을 지금의 자기개선 허용 경로에 곧바로 추가하지 않는다. 현재 역할이 바꿀 수 없는 대상은 신뢰할 수 있는 외부 실행자가 별도 검토·평가로 구축한다. 변경 종류별 회귀 과제를 먼저 확보한 뒤 자동 개선 범위를 따로 위임한다.

근거: [포스트모템 분석의 분류](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/packages/factory/src/postmortem/analysis.ts#L7-L18), [현재 자기개선 범위](https://github.com/roboco-io/the-software-factory-demo/blob/b925518f535b49f3383b23db52cc66e8139ce042/packages/factory/src/policy/improve-paths.ts#L5-L13).

## 적용 순서와 검토 상태

문서상의 의미 구분 → 공통 실행 명세/판본·증거 연결 → 수행 중 보안 경계 확인 → 복잡한 업무의 작업 계획 기록 → 정책 판정/개선 대상 분류 순서로 나눠 적용할 수 있다. 먼저 한 요청의 계획 변경과 실행·판정·관측을 끝까지 추적하는 시범을 권한다. 보안 경계를 확인하지 못한 상태로 권한과 자동화 범위를 확대하지 않는다.

확인한 범위에서 ‘계획과 하네스가 같은 객체이므로 전체를 갈아엎어야 한다’는 결론은 나오지 않았다. 다섯 개선은 현재 구조를 보존하면서 의미·추적·집행·개선의 연결을 강화하는 제안이다. P0로 재현한 결함은 없으며 전체 보안 적합성 판정은 하지 않았다. 제안의 수용 조건은 모두 구현·실행 검증 대기다.

점검 모드의 보고서와 출처/주장 매니페스트만 작성하고 세션/STATUS에 범위를 기록한다. 기존 독자용 출처 ID·원고·데모 해설·TL;DR·체인지 로그를 이 조사로 갱신하지 않는다. 테스트 실행·새 워크플로 실행·GitHub 이슈 생성·커밋·푸시·배포는 수행하지 않았다.
