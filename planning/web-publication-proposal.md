# The Software Factory 웹 공개 형식 제안

- 조사·제안일: 2026-10-13. 구현·배포 전 제안이며 선택된 기술이나 편집 확정으로 간주하지 않는다.
- 원고 기준: d99a03c. 서문·5부 20장·15개 패턴과 Markdown/JSON 연결을 활용한다.
- 사용자 확정: 로그인 없이 같은 브라우저에서 이어 읽기. 추가 요청: 역할·목적에 따라 필요한 장을 추천하는 질문형 안내 검토.
- 조사: Exa로 세 각도의 검색 결과 12건을 살펴보고 공식 사이트·문서 14개 URL의 관련 부분을 확인했다. 검색 실패 3회는 결과 수에서 제외했다. Starlight 확장 경로는 Context7 공식 문서로 보완했다. 검색 결과의 PDF는 통독하지 않았다. 브라우저에서 화면·성능·접근성을 시험한 결과는 아니다.

## 권장 형식

**온라인 책 + 패턴 사전 + 선택형 독서 안내**를 권한다. 장별 HTML을 기본 단위로 제공하고 기존 20장의 논증 순서를 유지한다. 독자는 처음부터 읽거나 자신의 문제에 맞는 경로를 선택한다. 패턴은 별도 URL에서 찾아보고 관련 장으로 돌아온다.

[Shape Up](https://basecamp.com/shapeup)은 부·장·절의 목차와 장별 페이지를 제공한다.[S76] 이 구조를 참고하되 화면 디자인이나 본문을 복제하지 않는다. 이 책에서는 순차 독서와 문제별 탐색을 함께 제공하는 것이 적합하다는 편집 판단이다.

| 형식 | 적합성 | 비용·제약 | 제안 |
|---|---|---|---|
| 온라인 책·패턴 사전 | 논증을 순서대로 읽고 패턴을 다시 찾기 좋음 | 책 읽기 화면과 진도 기능을 조정해야 함 | 기본 형식 |
| 블로그 연재 | 개별 글 공유·발행 알림에 적합 | 시간순 목록이 장의 순서와 어긋나기 쉬움 | 홍보·변경 안내에 사용 |
| PDF·전자책 | 다운로드·인쇄·오프라인에 적합 | 장 수정·검색·브라우저 이어 읽기 연결에 추가 작업 | 후속 보조 산출물 |

처음부터 화면 한 장에 책 전체를 넣거나 장 안의 모든 절을 별도 페이지로 나누기보다, 현재 한 장을 한 페이지로 사용한다. 논증의 앞뒤를 보존하고 장·절 링크로 바로 이동할 수 있게 한다.

## 화면과 정보 구조

홈에는 책의 약속·대상 독자·판본 상태를 짧게 소개하고 `처음부터 읽기`, `나에게 필요한 장 찾기`, `전체 목차`를 둔다. 방문 기록이 있으면 `이어서 읽기`를 먼저 보여준다. 소개보다 읽기 시작이 앞에 오도록 한다.

데스크톱은 왼쪽에 5부 20장 목차, 가운데 본문, 오른쪽에 현재 장의 절 목차를 배치한다. 모바일은 본문을 중심으로 책 목차·현재 장 목차를 접어 제공한다. 글자 크기·행간·줄 길이를 조정하고 긴 표는 작은 화면에서도 내용을 확인할 수 있게 한다. 읽음 표시는 색 외에 아이콘과 텍스트를 함께 쓴다. 이 배치는 제안이며 실제 원고로 가독성을 확인해야 한다.

| 영역 | 독자에게 제공할 내용 |
|---|---|
| 책 읽기 | 서문, 5부 20장, 이전·다음 장, 고정 절 링크 |
| 추천 경로 | 현재 목적에 맞는 3~5장, 추천 이유, 경로 진행 상태 |
| 패턴 사전 | P01~P15, 문제·조건·비용·연결 패턴·관련 장 |
| 참고문헌 | 본문이 실제 참조한 출처의 제목·작성자·원문·발표/확인 시점·확인 범위 |
| 책 소개·변경 이력 | 저자, 판본, 주요 내용 변경, 오탈자 제보 방법 |
| 읽기 설정 | 글자 크기·테마, 진도 저장 켜기/끄기·초기화, 추천 답변 수정 |

책 전체의 읽음 표시는 20장을 분모로 쓴다. 패턴 열람과 추천 경로의 완료는 따로 표시한다. 패턴을 열었다는 이유로 책의 진도가 올라가지 않는다. 본문 내용이 아직 초고라는 현재 상태를 고려하면 최초 공개판은 `공개 초안` 또는 `독자 검토판`으로 소개하는 안이 적절하다. 이는 공개판 편집 상태에 대한 제안이다.

## 질문형 독서 안내

역할별 진입 경로는 권한다. 다만 같은 개발 관리자라도 도입 투자와 검증 실패 해결에 필요한 장은 다르므로 **현재 목적을 우선하고 역할을 보조 조건**으로 사용한다. [GOV.UK 질문 지침](https://design-system.service.gov.uk/patterns/question-pages/)은 필요한 정보만 묻고 질문 이유와 되돌아갈 경로를 설명하도록 권한다.[S87] [Diátaxis](https://diataxis.fr/compass/)는 사용자가 배우려는지 적용하려는지를 문서 선택의 축으로 구분한다.[S88] 아래 장 추천은 이를 참고한 저자의 설계 제안이며 추천 효과를 입증한 것은 아니다.

첫 화면에서 선택할 수 있는 안내이며 질문을 건너뛰어 바로 목차를 열 수 있다. 책의 링크로 들어온 독자를 질문 화면으로 강제 이동시키지 않는다. 한 번에 한 질문을 보여주되 총 3개라는 점과 이전 답변 수정 기능을 제공한다.

1. **지금 해결하려는 문제는 무엇인가요?** 도입·투자 판단 / 결과 품질·검증 / 실행 권한·책임 / 팀 병목·협업 / 인간의 오너십·학습 / 전체 개념 이해. 한 가지 우선 목적을 선택한다. 아직 모르겠다면 입문 경로를 제공한다.
2. **어떤 역할에서 이 문제를 보고 있나요?** 경영진·임원 / 부서장·개발 관리자 / 팀 리더·실무 책임자 / 제품·사업 책임자 / 기타·응답 생략. 회사명·직급 등 세부 신상은 필요 없다.
3. **어느 깊이로 읽고 싶나요?** 핵심 판단만 훑기 / 관련 장을 정독하기 / 전체 흐름 따라가기. 시간은 실제 분량과 독자 시험으로 추정한 뒤 보조 정보로 붙인다. 몇 장을 특정 분 안에 읽는다고 보장하지 않는다.

### 처음 사용할 경로 예시

| 우선 목적 | 권장 순서 | 선택 이유 |
|---|---|---|
| AI 도입·투자 판단 | 1 → 9 → 17 → 18 → 20장 | 결과 선택 → 책임 구조 → 측정 → 최초 도입 → 확대 |
| 결과 품질·검증 | 5 → 7 → 8 → 11 → 12장 | 맡길 조건 → 완료 증거 → 실패 처리 → 조합 적격성 → 실제 권한 |
| 실행 권한·책임 | 3 → 5 → 9 → 12장 | 경계 → 계약 → 운영 책임 → 집행 |
| 팀 병목·협업 | 6 → 9 → 14 → 15장 | 작업·통합 → 역할 → 병목 → 경계 조정 |
| 인간의 오너십·학습 | 9 → 13 → 16 → 17장 | 실제 책임 → 역량 투자 → 참여 설계 → 결과·비용 평가 |
| 전체 개념 이해 | 1 → 2 → 3 → 4장 후 전체 목차 | 의도·정책·루프의 정의부터 시작 |

경로는 현재 장의 중심 주장·리더 결정과 대조했다. 원고를 새 요약본으로 대체하는 방식이 아니다. 깊이에 따라 같은 경로의 `핵심 판단` 안내 또는 전체 본문으로 들어간다. 핵심 안내 문장은 구현 단계에서 원고에 근거해 작성·검토한다.

초기 추천은 저자가 검토할 수 있는 규칙표로 구현하는 것을 권한다. 목적이 기본 경로를 선택하고, 역할은 강조할 장이나 인접 장의 우선순위에만 영향을 준다. 역할을 이유로 품질·권한의 선행 조건을 빼지 않는다. 최대 5개 장을 보여주고 추가 자료는 `더 읽기`로 분리한다. 입문 독자는 1장의 핵심 정의로 갈 수 있게 하되 이미 읽었다는 이유만으로 필수 개념을 영구적으로 감추지 않는다.

결과에는 `당신이 선택한 목적`, `이 장을 권하는 이유`, `먼저 알면 좋은 개념`, `다음에 판단할 것`을 표시한다. 같은 역할의 사람에게 단 하나의 정답을 판정하거나 역량 점수를 매기지 않는다. 추천 장을 교체하거나 전체 목차로 돌아갈 수 있다.

### 읽기 진도와 결합

예를 들어 품질·검증 경로의 5개 장 중 7장을 읽었다면 `추천 경로 1/5 읽음`으로 표시한다. 7장을 다시 권하더라도 `이미 읽음`을 보여주고 다음 미독 장으로 안내한다. 추천 답변을 바꿔도 기존 장별 읽음 표시는 보존한다. 본문 하단의 `다음 장`과 `추천 경로에서 다음`은 각각의 목적을 알 수 있게 구분한다.

질문 응답·선택 경로·마지막 읽던 위치는 같은 브라우저에 저장한다. 저장 목적을 안내하고 `추천 답변만 초기화`와 `모든 읽기 기록 초기화`를 구분한다. 추천 기능 때문에 계정이나 서버의 독자 프로필을 만들 필요는 없다. 첫 버전은 답변·진도에 대한 외부 분석 전송 없이 동작하도록 제안한다.

## 읽은 곳을 기억하는 동작

- **위치 자동 저장:** 마지막 장, 안정적인 절 ID와 절 안의 위치를 기록한다. 픽셀 좌표만 저장하면 글자 크기·화면 폭·원고 수정에 취약하다.
- **명시적인 읽음 표시:** 목차에 `안 읽음 / 읽는 중 / 읽음`을 표시한다. 페이지 끝에 도달하면 읽음 표시를 제안할 수 있으나 스크롤만으로 자동 완독 처리하지 않는다. 언제든 읽음 해제·다시 읽기를 선택한다.
- **이어 읽기:** 홈의 버튼이나 해당 장의 안내로 복원한다. 출처·절의 직접 링크로 진입했을 때는 그 링크의 목적지를 우선한다.
- **개정 처리:** 장 ID는 제목과 독립적으로 유지한다. 이전 판본에서 읽은 장은 의미 있는 개정 뒤 `읽은 뒤 수정됨`을 표시한다. 오탈자 수정마다 독자의 진도를 초기화하지 않는다.
- **저장 불가:** 브라우저 차단·저장 오류가 있어도 본문·검색·목차는 사용할 수 있어야 한다. 저장되지 않는 상태를 짧게 알리고 반복 오류창을 띄우지 않는다.
- **보존 범위:** 같은 브라우저·프로필·사이트 주소 기준이다. 다른 기기와 자동으로 이어지지 않으며 브라우저 데이터 삭제나 시크릿 모드 종료로 기록이 사라질 수 있다.[S84]

### 쿠키와 localStorage 비교

| 선택 | 장점 | 제약 | 판단 |
|---|---|---|---|
| localStorage | 읽기 상태·설정을 브라우저 안에 저장, 재방문 시 복원 | origin별 저장, 삭제·차단 가능, 기기 간 자동 동기화 없음 | 기본 권장 |
| 쿠키만 사용 | 마지막 장·읽음 여부 같은 작은 상태에 사용 가능 | 보통 쿠키당 약 4KB, 해당 요청에 자동 전송, 만료 관리 | 쿠키가 꼭 필요할 때의 대안 |
| 쿠키+localStorage | 서버도 알아야 하는 설정과 상세 진도를 나눌 수 있음 | 두 저장소 간 불일치·초기화 관리 추가 | 현재 범위에는 필요성 낮음 |

MDN은 브라우저 내 데이터 보관에 Storage API를 권하며 쿠키의 크기와 요청 전송 부담을 설명한다.[S83] 사용자가 요청한 재방문 편의는 localStorage로 충족할 수 있다는 기술적 판단이다. 아직 쿠키 대신 localStorage를 쓰는 기술 선택까지 확정한 것은 아니다.

쿠키를 고집할 이유가 있다면 마지막 장·절과 20장의 읽음 상태만 작게 저장하고 주기적으로 갱신한다. 쿠키의 범위·보존 기간·보호 설정은 선택한 배포 환경에서 확인한다. 쿠키가 차단됐을 때 저장소를 몰래 바꿔 사용자의 의도를 우회하지 않는다. 어느 방식이든 저장 켜기/끄기와 삭제를 제공한다. 법적 동의 의무를 여기서 단정하지 않는다.

## 출판 도구 비교

| 도구 | 공식 자료에서 확인한 기반 | 이 책의 추가 작업 | 판단 |
|---|---|---|---|
| Astro + Starlight | Markdown/MDX, 탐색·검색·테마, 컴포넌트 교체 [S79][S80][S81] | 책의 표지·본문 스타일, 읽기 진도, 독서 경로 | 권장: 검색·목차를 활용하며 독서 화면 확장 |
| mdBook | Markdown 책 생성, 통합 검색·테마·전처리 [S77] | 맞춤 홈·경로·진도 UI와 한국어 검색 확인 | 책만 빠르게 공개하는 대안 |
| Docusaurus | 정적 HTML·React/MDX, 버전 관리·다국어 [S78] | 책 중심 디자인, 진도·질문 UI | 여러 판본·언어 운영이 커질 때 재검토 |

이 평가는 기능 문서와 현재 원고 구조에 따른 제안이며 세 도구의 성능 비교 실험이 아니다. 읽기 진도와 역할 추천은 모두 추가 개발 범위다. Starlight가 원고를 아무 변환 없이 출판하거나 이 기능을 내장한다고 주장하지 않는다.

Starlight의 기본 검색은 Pagefind다.[S81] Pagefind 문서에서는 한국어 UI와 단어 어간 처리의 지원 수준이 다르다.[S82] 실제 의존 버전으로 `의도`, `의도의`, `실행 계약`, `P07`, `책임`을 찾아 필요한 장·패턴이 나오는지 확인한다. 한국어 품질이 부족하면 검색 별칭·메타데이터를 보완한 뒤 대체 검색을 판단한다.

## 원고에서 공개 사이트로 옮길 때

현재 원고를 계속 기준으로 쓰고 출판용 변환 단계에서 장 제목·순서·메타데이터를 만들도록 권한다. 제목과 독립적인 `ch01`~`ch20`, `p01`~`p15`를 유지한다. 링크·읽기 진도·추천 규칙이 제목 수정 때문에 깨지지 않게 한다.

발행 대상을 명시한다. 서문·장·패턴·공개 참고문헌·저자 소개·독자용 변경 이력만 사이트에 포함한다. 현재의 `planning/`, 리뷰 대장, 원고 주장 메모, STATUS와 로컬 파일 경로는 독자에게 필요한 설명으로 정리하고 내부 파일 자체를 배포하지 않는다. 연구 문서를 검색에서 숨기는 것만으로 파일 공개를 막을 수는 없다.

본문의 출처 표식은 공개 참고문헌의 고정 항목으로 변환한다. 현재 `research/sources.json`에는 집필·운영 메모와 이번 웹 설계 자료도 있으므로 원고가 실제 인용한 항목의 공개 필드만 생성한다. 날짜·직접 확인 범위·한계는 보존한다. 내부 주장 메모 링크를 그대로 남기지 않고 독자에게 필요한 확인 범위를 공개 출처 항목에 연결한다.

배포는 Git 변경→검사→미리보기→공개판의 흐름을 권한다. 새 Cloudflare 프로젝트라면 현재 Astro 공식 안내가 권하는 Workers 정적 자산 배포를 우선 후보로 삼는다.[S85] 기존 Pages 운영 환경이 있다면 그 선택도 가능하므로 새 서비스로 무조건 옮길 필요는 없다.[S86] 가격·계정·배포 권한은 이번에 확인하지 않았다. 도메인은 `factory.roboco.io` 같은 후보를 구현 전에 정하되 사용 가능 여부나 DNS를 확인한 것은 아니다. 기존 비공개 저장소의 공개 전환 없이 공개 산출물만 배포하는 구성을 제안한다.

## 구현 순서와 검증

1. 한 장·한 패턴으로 출판용 변환, 출처 링크, 책 읽기 화면을 만든다. 7장처럼 표·사례·외부 링크가 있는 장으로 확인한다.
2. 20장·15패턴의 목차·검색·이전/다음·모바일 화면을 연결한다.
3. 브라우저 진도 저장, 읽음 표시·해제, 위치 복원·초기화를 구현한다.
4. 질문 3개와 저자 검토 경로를 붙이고 진도와 연동한다. 역할 보조 규칙은 대표 독자 시나리오를 보고 다듬는다.
5. 링크·한글 검색·접근성·저장 실패·개정 처리·공개 파일 범위를 확인하고 공개판을 배포한다.

수용 기준은 새로고침·재방문·뒤로 가기·글자 크기 변경·모바일 폭·절 직접 링크·두 탭·저장 차단·기록 삭제·원고 개정에서 동작을 확인하는 것이다. 추천은 모든 답변 조합에서 존재하는 장만 가리키고, 중복·빈 경로가 없으며, 목적을 바꿔도 기존 읽음 표시가 보존되어야 한다. 건너뛰기·답변 수정·키보드 사용·저장 불가도 확인한다. 질문 응답이나 읽기 이벤트가 외부로 전송되지 않는지도 확인한다.

실제 독자에게는 추천 이유를 이해할 수 있는지, 원하는 문제를 다루는 장을 찾았는지, 다음 결정을 설명할 수 있는지 묻는다. 클릭률·완독 표시만으로 추천 효과나 이해도를 입증하지 않는다. 아직 이 검증이나 구현은 수행하지 않았다.

## 결정 상태

- 확정: 같은 브라우저에서 로그인 없이 이어 읽기.
- 권장: 온라인 책+패턴 사전+선택형 질문 안내, Starlight, localStorage, 목적 우선 규칙 추천.
- 구현 전 선택: 최종 도메인·호스팅, 공개판 표시와 저작물 이용 조건, 화면 스타일. 독자 추천의 효과는 실제 사용으로 검토한다.
