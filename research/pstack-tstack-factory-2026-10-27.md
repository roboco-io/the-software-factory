# Pstack·Tstack 조사와 소프트웨어 팩토리 적용 제안

## 결론과 확인 범위

2026년 10월 27일 기준으로, **Pstack의 검증 생성·유지관리와 Tstack의 변경 반영 흐름을 팩토리 하네스의 일부로 채택할 가치가 있다.** 다만 스킬 묶음 전체를 그대로 이식하거나 모델의 합의를 실행 허가로 삼는 방식은 권하지 않는다. 이 보고서의 적용 설계는 이 책의 제안이며 두 저장소가 성과를 입증했다는 주장이 아니다.

Exa의 성공한 검색3회에서 후보15개를 확인했다. 검색 축은 원본 Pstack의 출처/검증 방식과 Tstack의 리뷰/반영 방식 두 가지다. 원본 README·핵심 스킬·플레이북·매니페스트·라이선스 등 고정 판본 파일14개를 직접 읽었다. Pstack README는 앞부분과 플레이북 목록을 확인했으며 전체 가이드/23개 플레이북을 통독하지 않았다. 별도 미러의 README 앞부분은 출처 구분에만 사용했다. 스킬 설치·프로그램 실행·모델 리뷰·PR/CI 실행은 하지 않았다.

이는 저장소 기준 커밋의 시각이며 각 스킬의 최초 발표일이 아니다. Pstack은 플러그인 매니페스트의 저자가 Lauren Tan으로 표시된다. `backnotprop/pstack`은 원본과 구분한 독립 사용용 미러다. 인물의 현 소속·명성이나 ‘화제’의 크기는 이번 채택 판단의 근거로 사용하지 않았다.[S143][S155]

## 제공된 설명에서 보완할 점

### 1. Pstack은 검증 전용 묶음보다 넓다

원본 README는 업무에 맞는 플레이북 선택과 스킬 조합을 설명한다. 검증 생성/유지관리는 그중 특히 팩토리에 가져올 만한 부분이다.[S143] ‘Pstack은 검증, Tstack은 반영’은 비교의 초점으로는 유용하지만 두 저장소의 전체 기능 경계는 아니다. Tstack도 자체 증거를 요구한다.

### 2. 컴파일 증거를 버리는 것이 아니라 증거의 범위를 맞춘다

Pstack 생성 스킬은 사용자 경로와 결과·부수 효과를 관측하도록 지시한다. 생성한 검증 스킬을 한 기능에서 실제로 실행하고 정리 뒤에도 증거가 남는지 확인하게 한다. 초기 기능 지도는 주요3~5개로 시작하므로 생성 완료가 앱 전체 검증 완료는 아니다.[S144]

따라서 컴파일·정적 검사·단위 테스트가 무가치하다는 뜻으로 옮기면 안 된다. 이 책의 해석은 **컴파일 성공은 컴파일에 대한 증거이고, 사용자 동작의 증거를 대신하지 않는다**는 것이다. 스크린샷의 존재도 올바른 상태 전이와 부수 효과를 모두 입증하지는 않는다.

### 3. Tstack의 기본 리뷰 경로는 무한 합의 반복이 아니다

`full-send`는 `sol-loop`·PR 작성·CI/리뷰 대응을 조합한다.[S149] 확인 판본의 `sol-loop`는 기본3회, 지정된 위험 조건 등에서5회까지이며, 미해결 분쟁이나 한도 종료를 승인으로 취급하지 않는다.[S150] 다른 제공자3개의 모델을 모으는 `council`은 별도 스킬이고, 이 파일에는 명시적인 총 반복 상한이 없다.[S151] 기본 경로와 별도 패널을 구분해야 한다.

### 4. full-send에도 명시적인 위임과 한계가 있다

`full-send`는 명시적 요청과 현재 변경의 증거·검사·리뷰 상태를 병합 조건으로 둔다. 저장소의 보호 규칙 우회를 금지하고, 운영 환경 변경·데이터 삭제 등은 별도 질문 대상으로 둔다.[S149] `full-stop`은 같은 준비 흐름을 진행하되 병합과 자동 병합 설정 등을 하지 않는 별도 경계다.[S152]

이 책의 해석으로는 범위 안의 자율성과 개별 행동의 권한을 분리하는 사례다. 단, 자연언어 스킬의 지시가 실제 저장소·토큰 권한을 강제한다는 뜻은 아니다. 병합이 자동 배포를 촉발한다면 그 후속 영향도 미리 정한 위임 범위에 포함해야 한다.

## 팩토리 적용 설계 — 우선순위

### 1순위: 프로젝트별 검증 지도와 증거 계약

고객이 사용하는 기능·진입점·정상/실패 조건을 연결한 검증 지도를 만든다. 코드가 어떻게 생겼는지를 설명하는 목록보다 사용자가 무엇을 할 수 있어야 하는지에서 시작한다. 새 지도의 초기 범위와 아직 확인하지 않은 경로는 따로 표시한다.

| 연결할 항목 | 팩토리에서 남길 것 |
|---|---|
| 목적 | 고객 문제·기대 결과와 해당 기능이 기여하는 부분 |
| 준비 상태 | 대상 빌드/환경·데이터·권한·의존 서비스가 사용 가능한 조건 |
| 사용자 경로 | 진입점·조작·정상/예외·후속 상태 |
| 증거 | 현재 변경 버전, 실제 행동과 결과, 필요한 부수 효과, 확인하지 못한 조건 |
| 자원·정리 | 허용 데이터/외부 행동·실행 한도·자신이 시작한 자원만 정리하는 방법·남길 증거 |
| 책임 | 검증 자산 소유자·변경 권한·제품 결함의 처리 경로 |

이는 이 책의 확장 제안이다. 코드에서 실행 방법을 찾을 수 있어도 고객 문제·사업 우선순위·새 위임 범위를 코드만으로 확정하지 않는다. 빠진 선택은9장의 심층인터뷰처럼 의도와 권한을 가진 주체에게 확인한다. 보안·정보 전달·비용의 제약과 실제 사용자 결과를 더하고, Pstack의 특정 폴더나 도구 선택을 보편 규칙으로 가져오지는 않는다. 관련 장은5·7·10장, 관련 패턴은 P03 ‘실행 가능한 계약’, P06 ‘증거 기반 완료’, P13 ‘의도부터 결과까지 추적’이다.

### 2순위: 검증 자산의 드리프트와 제품 회귀를 구분

앱이 바뀌었다고 기대 결과를 자동으로 현재 동작에 맞추지 않는다. 의도가 승인된 경로로 바뀐 것인지, 검증 도구가 낡은 것인지, 제품의 회귀인지 먼저 판단한다. 유지관리 결과는 검증 자산의 정정·제품 결함 보고·확인 불가로 나눌 수 있다. 확인 불가는 통과가 아니다.

검증 기준의 갱신 권한과 제품 변경의 반영 권한을 나누고, 유지관리기가 제품을 바꾸어 자기 기준을 통과시키지 못하게 한다. 허용된 수정은 별도 정상/실패 사례로 평가하고 다음 실행에 적용한다. 4·10·19장과 P15 ‘검증을 거치는 개선’에 특히 잘 맞는다.

### 3순위: 현재 증거에 기반한 병합·배포 허용 판단

작은 스킬을 연결하는 방식은 채택하되, 단계 간에 문장 ‘완료’ 대신 버전과 상태를 전달한다. 최소한 의도/정책 판본, 변경 대상, 관측 증거, 필요한 검사/리뷰의 수행 상태, 남은 지적, 허용 권한과 예외 상태가 이어져야 한다.

자동 실행을 허용한 범위는 불필요한 승인 없이 진행한다. 필요한 증거가 없거나 정책상 사람 판단이 필요한 경우는 각각 보류와 이관으로 나눈다. 모델의 확신이나 합의는 그 경계를 바꿀 권한이 아니다. 반영 직전에는 현재 변경·기준 브랜치·검사·권한의 유효성을 다시 확인하고, 병합과 서비스 배포·사용자 결과 확인을 다른 상태로 기록한다. 9·12장, P10 ‘범위가 정해진 자율성’, P11 ‘예외를 통한 개입’에 연결한다.

### 4순위: 리뷰를 합의가 아니라 근거·한도·판정으로 운영

서로 다른 모델의 의견을 받는 방식은 후보 탐색과 반례 발견에 쓸 수 있다. 하지만 모델/제공자가 다르다는 사실만으로 독립성이나 안전성이 입증되지는 않는다. 조율자가 실제 근거를 확인하고 수용·반박·범위 밖·판정 불가를 남긴다.

Tstack의 기본 경로처럼 반복에는 비용·횟수·종료 조건을 둔다. 합의가 없거나 필요한 제공자에 접근할 수 없으면 그 상태를 기록하고, 다른 모델의 결과나 시간 초과를 승인으로 바꾸지 않는다. `council`을 쓸 때에는 별도의 한도를 추가한다. 보안·권한·데이터 손실·상태/동시성 문제는 실제 위험과 별도 증거로 다루고, 단순 ‘드문 경우’라는 이유로 필수 보호 조건을 낮추지 않는다. 7·11·19장, P07 ‘독립된 검증’에 연결한다.

### 5순위: 반복 실수는 정책과 집행 수단의 쌍으로 개선

에이전트에게 ‘다음부터 조심하라’를 추가하기 전에 잘못된 경로를 없앨 구조, 잘못된 상태를 표현하기 어렵게 할 타입, 위반을 거부할 CI/도구 권한을 검토한다. 판단이 필요한 부분은 자연언어 정책으로 남기되, 형식적으로 확인할 조건과 실제 행동의 집행은 실행 경계에 연결한다.

상위 원칙·검사·권한을 바꾸는 변경도 별도 평가 대상이다. 새 장치가 과거 실수를 거부하는지와 정상 작업을 과도하게 막지 않는지를 함께 확인한다. 모든 실수가 타입으로 사라진다는 주장이나, 판단을 문서화하지 말라는 규칙으로 일반화하지 않는다. 3·12·19장의 정책/집행 구분과 P15에 연결한다.

### 6순위: 측정 루프를 비즈니스 목표까지 확장

Pstack의 측정 규율을 쓰더라도 PR 수나 단일 성능 지표를 사업 성과와 동일시하지 않는다. 고객 문제에 맞는 대표 조건, 품질·보안·비용의 보호 조건을 먼저 정하고 가설별로 관찰한다. 원래 기준을 바꾼 변화와 같은 기준에서 더 잘 수행한 변화를 구분한다.

예를 들어 문의 업무에서는 초안 생성 시간만 줄이지 않고, 실제 해결 여부·재문의·근거의 정확성과 전체 처리 부담을 함께 본다. 수치의 개선과 인과적인 사업 효과는 다른 확인이다. 각 개선의 채택/보류/되돌림과 비용을 남긴다. 이는4·17·19장의 의도 개선과 하네스 개선을 잇는 저자 제안이며, 두 저장소에서 이미 사업 목표 달성을 입증했다는 뜻은 아니다.

## 그대로 적용하지 않을 조건

- **확신으로 사람 확인을 해제하지 않는다.** Tstack `full-send`에는 자동 리뷰의 사람 확인 권고를 확신에 따라 무시할 수 있다는 문구가 있다.[S149] 이 책에서는 단순 권고를 근거와 함께 불수용하는 것과 정책/보안/준법에서 정한 확인 의무를 해제하는 것을 구분해야 한다. 원문도 브랜치 보호 우회를 허용하지 않는다. 상위 원칙은 스킬 호출이나 확신으로 우회하지 않는다.
- **검증 실행을 운영 데이터 조작 허가로 읽지 않는다.** 테스트 범위·인스턴스 소유·외부 행동·정리·증거 보존을 정한다. 공유 사용자 세션과 운영 환경을 무심코 실험 대상으로 삼지 않는다. 자연언어로 허용한다고 적은 것과 실제 자격 증명을 가진 것은 별개다.
- **머지를 최종 사업 성과로 세지 않는다.** 배포가 촉발되는 연결과 실제 사용자 결과·보안·비용을 관찰할 책임을 포함해야 이 책의 비즈니스 목표 중심 자동화에 이른다.
- **스킬 이름과 도구 기본값을 원칙으로 만들지 않는다.** 특정 모델·제공자·봇·폴더는 교체될 수 있다. 현재 하네스가 실제로 실행할 수 있는지 확인하고 확인한 판본을 고정한다.

## 권하는 적용 순서와 완료 증거

| 단계 | 먼저 할 일 | 완료로 볼 근거 |
|---|---|---|
| 1 | 제품의 작은 사용자 여정에 검증 계약/지도를 작성 | 생성된 절차를 실제로 실행했고 증거가 정리 후에도 남음; 초기 범위·미확인 경로 표시 |
| 2 | 실행 증거를 현재 변경과 리뷰/CI 상태에 연결 | 다른 버전의 증거·결과 누락·정책상 금지를 정상 완료와 구분 |
| 3 | 검증 자산 유지관리와 제품 수정의 권한을 분리 | 낡은 지도/검증 도구 문제/제품 회귀를 구분한 사례와 정상 조건의 회귀 확인 |
| 4 | 병합·배포·운영 관찰을 정책 안에서 연결 | 허용 범위의 무승인 완주와 필수 이관·보류가 실제로 작동함을 확인 |
| 5 | 목표와 전체 부담을 대조하며 확대/보완/중단 | 고객 결과·품질·보안·비용의 관찰과 불확실성; 활동량만으로 확대하지 않음 |

책 사이트에서는 서문에서 장으로 읽기, 질문 기반 추천, 저장된 읽기 진도의 재개 같은 대표 여정을 초기 대상으로 삼을 수 있다. 이는 도입 후보이며 이번 조사에서 이 스킬로 실행했다는 뜻은 아니다. 데모에서는 요청·수행·검증·반영의 현재 구현과 먼저 대조해야 한다. 이번에 데모 최신 코드/운영을 재검증하지 않았으므로 새 구조가 이미 구현됐다고 표시하지 않는다.

책에는 새 챕터보다 **7장 검증 증거, 10장 공유 스킬, 12장 실제 허용 판단, 19장 유지관리/집행 개선**에 짧은 사례로 넣는 편을 권한다. `hillclimb`의 측정 규율은4·17장에 보조 연결하면 된다. 기존 정의와 패턴을 바꾸지 않고 구체 사례를 보태는 방향이다.
